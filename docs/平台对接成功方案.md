# 平台对接成功方案（现场已验证）

> 状态：2026-09-23 深夜 —— 平台联调**全流程通过**：启动游戏 / 开始游戏 / 结束游戏 / **调起平台客户端** 四项均在现场跑通。
> 依据：真实抓包（`平台指令/VRPlatform-流量取证/`、cap3.pcap）+ 现场实测，**不是推测**。
> 本文是**结论性方案**（口径 / 实现 / 判据 / 排障入口）；历史推演过程见 `docs/cast-architecture.md` 附录 C、D；
> 边界与诉求见 `docs/平台对接需求（对平台方）.md`。

## 一、成功路径总览：平台三步 ↔ 我方三步

| 步 | 平台动作 | 平台实际发出的报文（抓包实测） | 我方动作 | 现场观感 |
|---|---|---|---|---|
| ① | 点「**启动游戏**」 | 启动器通道 UDP **62135**：`{"cmd":"start","msgData":"<目录>\DeepmindHacker.exe$DeepmindHacker$<平台IP>"}` → `DoStartGame` → `CreateProcess` | 拉起**平台登记的那个 EXE**（= 我们的直播接收端）+ 拉起头显 APK | PC 出现接收端窗口；头显显示「⏳ 等待平台点「开始游戏」…」 |
| ② | 点「**开始游戏**」 | 游戏通道 UDP **51124**：`\x05{"difficulty":0,…,"gameId":128,…}`（GameStart；**只发给「跑游戏的那台机器」**） | EXE 回 118 字节确认帧 + **放行本局**；头显页面 ≤2s 内开闸 | 头显出现**蓝 / 红二选一按钮** → 点进 VR；PC 大屏出画面 **+ 声音** |
| ③ | 点「**结束游戏**」 | 并发三路：启动器 `{"cmd":"kill"}` + 游戏通道 `\x10 "closeGame␠␠"` + `logcat` | EXE 被平台结束；头显退 VR → 卸载页面 → **把平台客户端顶回前台** | 头显回到**平台客户端界面**（不是白页）；再点「启动游戏」能重新拉起 |

> 一句话记忆：**① 拉起进程 → ② 放行开局 → ③ 收回并交还前台**。三者走**不同通道**，缺一不可，且都已被抓包钉死。

## 二、成功的前提（三条必须同时对上）

| 前提 | 内容 | 对不上会怎样 |
|---|---|---|
| **登记** | 平台里登记的「游戏」必须是**我们的 PC 端 EXE**：启动器 `start` 的 `msgData` 第一段路径 / 第二段进程名与它一致 | ② 的 GameStart 打不到我们；③ 的 `kill` 也杀不到我们 |
| **包名** | 头显 APK `com.GoodNet.DeepmindHacker`（versionName 2.0.5 / versionCode 205）；平台客户端 `com.GoodNet.LauncherClient` | ① 拉不起头显端；③ 顶不回客户端 |
| **网络** | 同网段；PC 侧 **UDP 51124 可被平台打到**（勿被其它进程占用）；头显侧 UDP 51124 同理 | ② 收不到 → 头显永远停在等待页 |

- **EXE 启动参数**（平台拉起时带；全部可选）：位置参数 `<exe路径>$<进程名>$<平台IP>`，或 `--room=` / `--platform=` / `--game=`。
- 不带任何平台参数地手动双击 EXE = **排练模式**：不放行本局，用 PC 窗口的 `▶ 开始本局`（快捷键 `S`）手动放行，其余流程完全一致。

## 三、①「启动游戏」成功方案

- **PC 侧**：`PLATFORM_LAUNCHED` 解析成功 → 窗口顶部显示平台参数（房间/平台 IP/游戏名）、日志写「本次由平台「启动游戏」拉起（第一步）」。
  ⚠ 它**只用于显示与留痕**，**不参与放行** —— 第十九修曾拿它当开局信号，结果「平台刚点启动游戏，头显就冒出进入 VR」，已被推翻。
- **头显侧**：APK 起来后起本地服务（`localhost:8080`，WebXR 安全上下文），再拉起 PICO 浏览器到
  `http://localhost:8080/?cast=1&pc=<PC>:<端口>&mode=webrtc&plat=1`。
- **页面侧**：门禁**关着**（`?plat=1` 不是开局信号，第十八修的结论未回退），显示
  「⏳ 等待平台点「开始游戏」…」。

## 四、②「开始游戏」成功方案（本方案的核心）

### 4.1 抓包事实（决定了实现口径）

| 事实（实测） | 由此得到的结论 |
|---|---|
| GameStart(`0x05`) **只发给跑游戏的那台机器**（`20:49:56 .237:58734 → .237:51124`），头显 `.228` 没收到 | 头显侧**不能假定**能收到 ⇒ 必须留 PC 侧回报兜底 |
| closeGame(`0x10`) 是**两路同发**（→ PC 的 51124 **和** → 头显的 51124） | 关游戏两端都能直接收到，不需要互相转达 |
| 真实游戏收到 `0x05` 会**回 118 字节确认帧**（`flag=1`） | 我们照抄回一帧，平台才认为「游戏已开局」 |
| 注册是 `0x01`（1 字节），**源端口必须 51124** | 用临时端口发，平台回包会打到别处，就永远等不到机位表 |
| 平台 57ms 后回「机位表」`0x01 0x02 + {"Machines":[…]}` | **机位表 = 平台认到本机的唯一凭证**（也是"注册生效"的现场证据） |

### 4.2 PC 侧实现（`tools/cast-pc/main.js` · §平台游戏通道）

```js
const GAME_CH_PORT = 51124;        // 平台 → 本机（真实游戏日志里的 sendUDPPort）
const GAME_CH_ACK_PORT = 51234;    // 本机 → 平台（recvUDPPort）

0x01  → 注册：bind 51124 后 0 / 1.5 / 3 / 4.5s 各发一次（源端口 51124，抗 UDP 丢包）
0x05  → roundSet(true, '平台「开始游戏」（CMD 5 GameStart gameId=…）')  + 回 118B 确认帧
0x10  → roundSet(false, '平台「关闭游戏」')                              + 回 0x02
0x01 0x02 + JSON → 机位表：记 machines 条数（平台已认到本机）
```

- `round.armed = true` ⇒ 头显页面轮询 `/api/master/allow` 即放行，**现场操作员一次按钮都不用点**。
- 新增 `POST /api/round/start`：头显页面收到 cmd 21 后**回报**过来，覆盖「平台只把 GameStart 发给 PC」的时序差。
- 排障第一眼看 `/api/info.gameChannel`：`bound`（有没有 bind 上 51124）/ `frames`（收到几帧）/
  `machines`（平台认到本机了吗）/ `lastStartAt` / `lastStartFrom` / `why`。

### 4.3 头显 APK 侧（`VRPlusLink.java`）

```
recvLoop:
  b0 == 0x05  → handleGameStart() → inbox 入队 {"cmd":21,"plat":true,…} + 回 118B 确认帧
                ⚠ 必须排在 closeGame 判断之前（否则先被当杂散帧丢掉）
  b0 == 0x10  → handleCloseGame() → inbox {"cmd":16} + 回 0x02
  机位表      → inbox {"cmd":0}（页面只记录，不当作业务命令）
```

### 4.4 页面侧（`src/game/game.js` → `src/main.js`）

```
game.js  : inbox cmd 21 → platformHooks.onStart('平台「开始游戏」（CMD 5 GameStart）')
main.js  : onStart → vrPlatStart = true → setVRGate(true) → 回报 POST /api/round/start
           → 门禁开 → 出现二选一按钮（蓝 ⚡射速加倍·攻击力减半 / 红 💥攻击力加倍·射速减半）
           → 点任一个都直接进 VR，并按倍率改本局初始属性（LOADOUTS）
```

- **残留清理**（很重要的一个坑）：新一局开始时必须丢弃上一局的 `cmd==21` 与 `cmd==3 && plat` 帧
  （`_pageT0` / `clearStaleClose()`），否则上一局的开局信号会把新一局的门禁顶开 —— 现象正是
  「平台还没点开始游戏，头显就冒出了进入 VR」。
- **二选一按钮**（本版新增）：蓝 = 射速加倍 / 攻击力减半（攻击力 100→**50**、射速 2→**4 发/秒**）；
  红 = 攻击力加倍 / 射速减半（攻击力 100→**200**、射速 2→**1 发/秒**）。只改**初始值**，
  后续抽卡（+100 攻击 / +2 射速）与死亡重开（+50 攻击）照旧在其之上叠加。
### 4.5 放行判据（一条公式，现场照它核对）

```js
// src/main.js
masterGateAllowed() = !MASTER_GATE_ON          // 调试包 / ?gate=0 → 直接放行
                   || vrMaster.exempt          // PCVR 桌面模式
                   || vrPlatStart              // ★ ② 平台真的说了「开始游戏」（inbox cmd 21）← 正常路径
                   || (vrMaster.known && vrMaster.ok);   // PC 主控端回了「允许运行」（门禁兜底路径）
```

- 门禁是**双保险**：APK 侧拿不到 PC 放行就停在提示页；游戏页面侧再校验一次，防止绕过 APK 直接进游戏。
- 正式包 `MASTER_GATE = true`（硬拦）；`?gate=0` 与调试包放行，保证现场自测与「直连 PC 兜底诊断」不受影响。

### 4.6 兜底（防软锁，三条并存）

| 兜底 | 触发条件 | 效果 |
|---|---|---|
| 30 秒无条件放行 | 页面起来后 30s 内**没收到任何**开局信号（`VR_GATE_FALLBACK_MS`） | 直接开门禁，现场不会卡死 |
| PC 手动放行 | 排练 / 平台通道异常时，点 PC 窗口 `▶ 开始本局`（快捷键 `S`） | 走同一套 `roundSet(true)`，链路完全一致 |
| 头显回报 | 页面收到 cmd 21 后 `POST /api/round/start` | 平台只把 GameStart 发给 PC 时，PC 侧仍能拿到结论 |

### 4.7 成功判据（三条同时成立，这一步才算过）

1. 头显 **≤2 秒**从「⏳ 等待平台点「开始游戏」…」变成**二选一按钮**。
2. PC 端 `http://127.0.0.1:<端口>/api/info`：`round.armed=true`、`gameChannel.lastStartFrom` 有值、`machines ≥ 1`。
3. 点进 VR → PC 大屏出画面 **和声音**；EXE 日志依次出现
   `推流端已上线` → `收到推流端 offer` → `已发出 answer` → `收到远端媒体流，开始显示画面 ✅`。

## 五、③「结束游戏」+ 调起平台客户端成功方案

### 5.1 两路触发（谁先到算谁，只执行最早那次）

| 来源 | 报文 / 事件 | 执行延迟 |
|---|---|---|
| **平台关游戏** | 游戏通道 `0x10 "closeGame␠␠"` → `VRPlusLink.handleCloseGame()` → `GameServer.sCastRoundOver = true` | **0 ms**（`RESTORE_FAST_MS`；原因是平台紧接着就 force-stop 本 APK） |
| 页面上报 | 本局自然结束（打输 / 通关 / 主动退 VR）→ `game-end` → `GameServer.sOnGameEnd` | 8 s（留给结算画面走完） |
| 平台杀进程 | 启动器 `{"cmd":"kill","msgData":"DeepmindHacker"}` | 平台侧行为：EXE 直接消失（**正常**） |

> 执行前会复核「期间没有开新的一局」（比对 `sLaunchedAt`），避免误伤下一局。

### 5.2 为什么必须「顶客户端」——这一步以前是失败的

现场现象：平台关游戏后，**头显浏览器停在 `about:blank` 白页，而平台客户端 `com.GoodNet.LauncherClient`
仍留在后台** ⇒ 平台下一次「启动游戏」拉不起头显里的游戏（**第二次启动必然失败**）。

根因两条（第十九修失败的原因）：
① `scheduleClientRestore()` 默认等 2.5s，而平台是**并发 force-stop** 本 APK，等待窗口根本不够；
② `bringClientToFront()` 只顶一次，且复核回调在直播分支里跑不到 ⇒ 变成"永远不关浏览器"。

### 5.3 实现要点（`MainActivity.java`）

```
scheduleClientRestore(app, why, delay):
    why 含 "closeGame" ⇒ delay 归 0（RESTORE_FAST_MS）

bringClientToFront(app, why):        ← 连顶 3 次，把机会全挤进"被杀之前"的窗口
    #1  0ms    NEW_TASK | REORDER_TO_FRONT
    #2  600ms  + RESET_TASK_IF_NEEDED | BROUGHT_TO_FRONT     （有些 Unity 启动器只有 reset 才把主 task 提上来）
    #3  1200ms + CLEAR_TOP | SINGLE_TOP
        若 getLaunchIntentForPackage() 为 null ⇒ 兜底 Intent: MAIN + LAUNCHER + setPackage

verifyClientFront(app, pkg, why):    ← 1.2s 后**实测**：页面还在打点=没生效；打点停了才算成功
restoreClientAndCloseBrowser():      顶客户端 → 固定 1.2s 后 killBrowser（不再等实测回调）
```

**成功率的第一决定因素：悬浮窗权限。** Android 10+ 从后台 `startActivity` 会被系统**静默丢弃**
（不抛异常、也不生效），所以必须在头显客户端里给本 APK **授予悬浮窗权限**（APK 配置页有「授予悬浮窗权限」按钮）。
留痕会直接把结论写出来：「悬浮窗权限=**未授予**（后台 startActivity 会被系统静默丢弃，这就是顶不动客户端的头号原因）」。

### 5.4 成功判据

1. 头显**停在平台客户端界面**（不是白页、不是浏览器）。
2. PC 端 EXE 被平台结束（接收端窗口消失）。
3. **再点一次「启动游戏」能正常拉起**（第二次启动不复现失败）。

### 5.5 排障入口

- 头显：`http://<头显IP>:8080/api/page/forensics?download=1` —— 看「悬浮窗权限=已授予/未授予」、
  「已发出顶客户端请求 #1/#2/#3」、「已收到平台关闭指令（0x10 closeGame）」、「已生效 / 未生效」。
- PC：`http://127.0.0.1:<端口>/api/info` 的 `gameChannel.lastCloseAt` + EXE 窗口日志。

## 六、端到端时序（现场实测口径）

```
平台                启动器通道(62135/62136)     游戏通道(51124/51234)          头显 APK                PC EXE
 │ 点"启动游戏" ─start─► 启动器 ─CreateProcess──────────────────────────────────────────────────► EXE 起来
 │                      └─am start───────────────────────────────────────────► APK 起来 → 拉起浏览器
 │                                                                             页面：门禁关（等待开始游戏）
 │                                                                    ◄─0x01 注册─  (bind 51124，源端口 51124)
 │  ──机位表─────────────────────────────────────────────────────────► (Machines=N) = 平台认到本机
 │ 点"开始游戏" ─0x05 GameStart─► 51124 ─────────────────────────────────────► EXE: round.armed=true + 回118B
 │                                                                             页面轮询 /api/master/allow → 开闸
 │                                                                             出现二选一按钮 → 点进 VR ──► 大屏出画面
 │ 点"结束游戏" ─kill─► 启动器(杀 EXE)────────────────────────────────────────────────────────────────► EXE 关闭
 │              ─0x10 closeGame─► 51124(PC) 与 51124(头显) ─────────────────► 退 VR → 卸载页 → 顶客户端回前台
```

## 七、现场验收清单（逐条打勾）

1. 平台点「启动游戏」→ PC EXE 起来（顶部显示平台参数）+ 头显起来；**头显不出现「进入 VR」**，
   显示「⏳ 等待平台点「开始游戏」…」。
2. 平台点「开始游戏」→ 头显出现**二选一按钮**（蓝 ⚡射速加倍·攻击力减半 / 红 💥攻击力加倍·射速减半）；
   点任一个都直接进 VR，腕表初始值符合所选（蓝 攻击力 50 / 射速 4；红 攻击力 200 / 射速 1）。
3. PC 端 `/api/info`：`round.armed=true`、`gameChannel.lastStartFrom` 有值、`machines ≥ 1`。
4. PC 大屏：影片播放前显示**清晰**等待文案；影片期间播本地影片（有声音）；进第 1 关自动切游戏画面。
5. 平台点「结束游戏」→ EXE 关闭 + 头显退 VR + 浏览器退掉 + **平台客户端回到前台**。
6. **第二次启动**：再点「启动游戏」→ 能正常拉起（不复现失败）。
7. 门禁三态：正式包 + PC 未放行 → 拦并提示；拿到放行 → 正常进 VR；调试包 / `?gate=0` → 放行。
8. 排练路径：手动双击 EXE（不带平台参数）→ 用 PC 的 `▶ 开始本局` / `■ 结束本局` 完整演练一遍。

## 八、仍需平台方配合（不阻塞现场，属优化项）

| 项 | 现状 | 诉求 |
|---|---|---|
| 「开始游戏」送达范围 | GameStart **只发跑游戏的那台机器**，头显拿不到，靠 PC 回报兜底 | 若能同帧也发给头显（像 closeGame 那样两路同发），可省掉约 0.5~2s 的兜底延迟 |
| 「游戏结束」上行报文 | 我方已本地留痕（`game-end`），无平台定义的上行格式 | 平台给出上行的指令定义，我们按其格式补发 |
| 启动器 `close game path` | 现场 `kill` 已能杀掉 EXE（正常） | 若后续有更细的收尾要求（如"先卸载页面再杀进程"），请给出时序 |
| 包标识与签名 | APK `com.GoodNet.DeepmindHacker`，debug 签名 | 平台登记须与之一致；改签名会影响升级（详见 `docs/平台对接需求（对平台方）.md`） |
