# 关卡内容授权门禁设计（Content Grant）

> 目标读者：本项目开发者 / 运维。
> 定位：把「关卡数据」从**随安装包分发**改成**每次启动向授权服务器换取**，
> 并补上目前只覆盖头显、**未覆盖 PC 端**的那一半。
>
> 状态：**设计定稿，待实现**。
> 关联文档：`docs/tech/08-授权服务器与License方案.md`（授权体系全貌）、
> `docs/cast-implementation-and-packaging.md`（双端打包）、`docs/cast-architecture.md`（踩坑史）。

---

## 1. 一句话结论

**关卡数据本地不留源，每次 EXE 启动向授权服务器换取；断网即停。**

强度定位要诚实：这是**提高门槛**，不是绝对防护。真正的收益是
「**正常途径绕不过**」——删文件、断网、拷机器、搭假服务器这四类常见规避全部失效。

---

## 2. 需求与决策（已拍板）

| 项 | 决策 | 影响 |
|---|---|---|
| 断网策略 | **硬档：断网即停** | 无离线条款；授权服务器成为**每次启动的硬依赖** |
| 搬运范围 | **只搬 `src/content/` 五个文件** | `src/core/userConfig.js` 暂留本地，以后再看 |
| 内容版本化 | **必须做**（见 §9） | 不做会出事故：1.0 客户端拿到 2.0 关卡数据 = 崩 |
| 计费口径 | 按年订阅 | 影响 TTL 配置，不影响本方案结构 |
| 公司自发授权 | **不允许** | 多租户后台砍掉；`/api/content/grant` 无需子账号体系 |

## 3. 现状核查：哪把锁已经有了

**好消息：要用的零件基本现成，而且模式已经跑通。**

| 已有零件 | 位置 | 作用 |
|---|---|---|
| 局号 `SESSION_ID` | `tools/cast-pc/main.js:611` | 每进程随机 4 字节；头显存盘，下次对不上即整包重下 |
| 下发清单 `CONFIG_MANIFEST` | `tools/cast-pc/main.js:618-621` | 正是 `['src/content/', 'src/core/userConfig.js']` |
| 下发接口 `/api/config/dump` | `tools/cast-pc/main.js:1068` | 双门禁：`licenseGate()` + `guardVerify()` |
| 「只认下发不回落」 | `tools/cast-pc/main.js:616-617` 注释 | 原文：「它们就是**文件齐全才跑得起来**的那把锁，别把它改成可回落」 |
| 签发私钥 `Ks` / 验签公钥 | 服务器 `secrets/license-sign.pem`；两端硬编码 `LICENSE_PUBKEY_B64`（`main.js:644`） | 内容包签名直接用这一套 |
| 实例密钥 `Ke` + proof 模式 | `main.js:678` `licenseSign()`；服务器 `handleRenew` 的 `proof` 校验 | **照抄即可，不发明新密码学** |

### 3.1 缺的那一半（本方案要补的）

**锁只锁了头显，PC 端没锁。**

- 头显取内容走 `/api/config/dump` → 有门禁、有局号 ✓
- PC 端页面取内容走 `handleStatic`（`main.js:342`）→ 从 `GAME_ROOT` **磁盘直读**（`main.js:380-387`），**无任何门禁** ✗

只要 PC 端这一头敞开，「缺文件玩不了」就不成立：磁盘上永远有源。

### 3.2 一个关键结构事实（决定实现方式）

**`GAME_ROOT` 是外部目录，不在 EXE 安装包内。**

来源优先级（`main.js:89-99`）：`--game-root=` CLI > `userData/cast-pc-config.json` > 自动探测
（含 `E:/AI_Work/WebXR_Begain` 等常见路径）。

而 `package.json` 的 `build` **没有 `files` 字段**、`asar: true`，`src/` 又不在 `tools/cast-pc/` 之下
⇒ **EXE 安装包本来就不含关卡数据。**

**推论：不需要改打包配置。** 要改的是两件事：

1. **部署规范**：装机时游戏目录里**不放** `src/content/`；
2. **启动自检**：EXE 若在 `GAME_ROOT` 里发现 `src/content/`，**报警并拒绝托管**
   （防装机员图省事拷完整目录，人为把锁拆掉）。

### 3.3 为什么「缺文件就玩不了」天然成立

`src/content/` 五个文件被**静态 import**，缺任一即模块解析失败 → 页面白屏：

| 文件 | 被谁 import |
|---|---|
| `src/content/levels.js` | `src/main.js:10`、`src/game/game.js:15`、`src/game/waves.js:4` |
| `src/content/spawnPlans.js` | `src/game/game.js:16`、`src/game/waves.js:5` |
| `src/content/enemies.js` | `src/game/balloons.js:2`、`src/game/waves.js:3`、`src/game/difficultyController.js:13` |
| `src/content/cards.js` | `src/game/cardDraft.js:3` |
| `src/content/levelConfig.js` | （由上述模块间接引用） |

**注意：这是「物理缺文件」的强，不是「一段删除逻辑」的弱。** 本方案的强度来自
「本地根本没有源」+「服务端签名」，而不是「启动时删了一下」。

## 4. 协议规范：`POST /api/content/grant`

### 4.1 请求

```json
{
  "lic":  "L20260920-0001",
  "dev":  "<机器指纹 sha256 hex>",
  "ke":   "<本机实例公钥 base64url(SPKI DER)>",
  "ver":  "1.0.0",
  "ts":   1758600000000,
  "proof": "<base64url( ECDSA-P256-SHA256(Ke_priv, \"content|L20260920-0001|1758600000000\") )>"
}
```

- `proof` 的待签文本 = `content|<lic>|<ts>`，**严格照抄 `renew` 的 `proof` 构造方式**
  （服务器 `handleRenew` 用 `renew|<lic>|<ts>`）。
- 用 `Ke` 签名 ⇒ 请求本身无法被拷到别的机器重放（服务器会拿该 lic 记录的 `ke` 验签）。

### 4.2 响应（成功）

```json
{
  "ok": true,
  "lic": "L20260920-0001",
  "ke": "<回显，便于客户端自检>",
  "ver": "1.0.0",
  "session": "<服务器随机 16 hex>",
  "iat": 1758600000000,
  "exp": 1758600900000,
  "manifest": [
    { "path": "src/content/levels.js", "sha256": "<hex>", "size": 4096, "content": "<utf8>" }
  ],
  "sig": "<base64url( Ks_sign(\"content|L20260920-0001|<ke>|<session>|<iat>|<exp>|<manifestSha256>\") )>"
}
```

- `manifestSha256` = 把 `manifest` 按**数组顺序**拼 `path + '|' + sha256 + '\n'` 后再 sha256，
  保证「清单顺序也受签名保护」。
- `exp` 当前取 `iat + 15 分钟`。这个值是**内容包的内存/磁盘寿命**，与 license 的 15 天 TTL 无关：
  硬档下 EXE 每次启动都重新换，短 `exp` 只是进一步压缩「囤积复用」的窗口。

### 4.3 响应（失败）

统一 `{ ok: false, reason, detail }`，`reason` 取值与 `handleRenew` **保持同一套词汇**：

| reason | HTTP | 触发 |
|---|---|---|
| `badParam` | 400 | 缺 `lic/dev/ke/ver/ts/proof` |
| `stale` | 400 | `abs(now - ts) > 5min`（`lib.SKEW_MS`） |
| `notFound` | 404 | license 不存在 |
| `noContentVersion` | 404 | 服务器没有该 `ver` 的内容目录（**这是发版事故信号**） |
| `revoked` | 403 | license 已吊销 |
| `machineMismatch` | 403 | `dev` 不匹配 |
| `keyMismatch` | 403 | `ke` 不匹配 |
| `badProof` | 403 | proof 验签失败 |
| `rateLimit` | 429 | 限流 |

**校验顺序必须与 `handleRenew` 完全一致**（存在 → 吊销 → dev → ke → ts → proof），
否则会出现「用错误信息探测 license 是否存在」的信息泄漏。

### 5.2 `server.js` 改动

| 位置 | 改动 |
|---|---|

`handleContentGrant` 骨架（伪码，与 `handleRenew` 同构）：

```js
function handleContentGrant(req, res, body) {
  const ip = clientIp(req);
  const { lic, dev, ke, ver, proof } = body;
  const ts = Number(body.ts);
  if (!lic || !dev || !ke || !ver || !Number.isFinite(ts) || !proof)
    return json(res, 400, { ok:false, reason:'badParam', detail:'缺少 lic/dev/ke/ver/ts/proof' });

  const row = store.licenses.get(lic);
  if (!row)             return json(res, 404, { ok:false, reason:'notFound', detail:'license 不存在' });
  if (row.revoked)      return json(res, 403, { ok:false, reason:'revoked', detail: row.revoked_reason || '已被吊销' });
  if (row.dev !== dev)  return json(res, 403, { ok:false, reason:'machineMismatch', detail:'机器指纹不匹配' });
  if (row.ke !== ke)    return json(res, 403, { ok:false, reason:'keyMismatch', detail:'实例公钥不匹配' });
  if (Math.abs(Date.now() - ts) > lib.SKEW_MS)
    return json(res, 400, { ok:false, reason:'stale', detail:'时间戳偏差超过 5 分钟，请校时' });
  if (!lib.verifyText(ke, 'content|' + lic + '|' + ts, proof))
    return json(res, 403, { ok:false, reason:'badProof', detail:'持有证明验签失败' });

  // ★ license 时间窗：过期即拒（硬档）
  const t = lib.checkTime(row, Date.now());
  if (!t.ok) return json(res, 403, { ok:false, reason: t.reason, detail: t.detail });

  const loaded = loadContentVersion(ver);           // 读 content/<ver>/src/content/*
  if (!loaded) return json(res, 404, { ok:false, reason:'noContentVersion', detail:'服务器无此内容版本：' + ver });

  const session = crypto.randomBytes(8).toString('hex');
  const iat = Date.now();
  const exp = iat + CONTENT_GRANT_TTL_MS;           // 15 分钟
  const manifestSha256 = sha256Manifest(loaded.manifest);
  const sig = lib.signText(SIGN_PRIV,
    ['content', lic, ke, session, iat, exp, manifestSha256].join('|'));

  log(`content 授权 lic=${lic} ver=${ver} 文件=${loaded.manifest.length} ip=${ip}`);
  return json(res, 200, { ok:true, lic, ke, ver, session, iat, exp,
                          manifest: loaded.manifest, sig });
}
```

新增常量（放在 `TTL_MS` 附近，L73）：

```js
/** 内容包有效期（毫秒）—— 只影响「囤积复用」窗口，硬档下每次启动都会重新换 */
const CONTENT_GRANT_TTL_MS = 15 * 60 * 1000;
```

### 5.3 不需要改的部分

- 数据库：内容不放 DB，放文件系统（内容变更必然伴随发版，用目录版本化更直观）
- 管理后台：本方案不需要新页面（公司不能自发授权，无多租户）

目录会残留；只有「启动无条件清」能兜住。这个教训头显侧已经吃过一次，原注释在
`main.js:608-610`：

> 「等价于「退出即失活」，但不会在错误时机真删文件（Activity 销毁时真删，
> 会把平台重拉后正在跑的游戏页资源删掉）」

现状只有 `app.on('window-all-closed', ...)`（L583），**没有 `before-quit`**。新增：

### 6.5 托管拦截（**核心**）

`handleStatic`（L342）目前无条件从 `serveRoot` 读磁盘（L380-387）。在 `L376` 之后、
`L380` 之前插入：

```js
// ★ 内容门禁：/src/content/* 只认 grant，绝不回落 GAME_ROOT（与头显侧 overlay 同口径）
if (rel.startsWith('/src/content/')) {

  if (g.startsWith(CONTENT_DIR) && fs.existsSync(g) && fs.statSync(g).isFile()) {
```

## 7. 部署规范（**必须写进装机手册**）

| 项 | 规则 |
|---|---|
| 游戏目录内容 | **不放 `src/content/`**。其余照旧（`index.html`、`vendor/`、`src/` 的其他子目录、`assets/`、`Sky/`、`Model/`） |
| 为什么 | `src/content/` 是**关卡数据**，改由服务器下发 |
| 装机自检 | EXE 启动若在 `GAME_ROOT` 发现 `src/content/` → 控制台告警 + 接收端界面红字 |
| 如何满足 | `GAME_ROOT` 指向的目录**用部署包生成**（`node tools/cast-pc/make-deploy.js`，待实现），而不是直接拷开发目录 |

⚠ **这是整套方案里最容易被人为破坏的一环。** 装机员图省事把完整项目目录拷过去，
锁就自动失效了——而且**不会报错**，只会静默从磁盘读。所以 §6.3 的启动自检是必需的，不是可选的。

## 8. 失败模式与提示文案（硬档）

| 场景 | EXE 行为 | 用户看到 |
|---|---|---|
| 未激活 | 不换包 | 接收端界面：「直播端未激活：请在接收端界面填入激活码」（已有文案，L909） |
| license 到期/无效 | 不换包 | 「授权无效（…）—— 需要重新激活」（已有，L883） |
| license 有效但**服务器不可达** | `contentReady()=false` | 接收端：「⚠ 授权服务器不可达，本机无法启动游戏」；页面 `/src/content/*` 返回 404 + 说明文本 |
| license 有效但**服务器无该内容版本** | 同上 | 「服务器无内容版本 1.0.0 —— 请检查是否漏跑 sync-content.js」 |
| 内容包被篡改（sha256 不符） | 拒用 | 「内容包校验失败 —— 请检查网络是否被劫持」 |
| `GAME_ROOT` 残留 `src/content/` | **仍按门禁走**（不从磁盘读），但告警 | 「⚠ 检测到本地残留关卡数据，请从部署目录移除」 |

**关键：任何失败都不回落磁盘。** 这是与「头显侧 overlay 只认下发」的同一口径。

## 9. 内容版本化（不做会出事故）

**事故形态**：你发布了 2.0 游戏（关卡结构变了），但服务器上 `content/` 还是 1.0 的。
装了 2.0 的客户端请求时，服务器按默认返回 1.0 内容 → **关卡数据与代码不匹配 → 运行期崩溃**，
而且报错位置离根因很远。

**约定**：

1. EXE 内置 `CONTENT_VER`（§6.1），请求时上报 `ver`；
2. 服务器**只按 `ver` 精确匹配**目录，**没有就返回 `noContentVersion`**，绝不回落 `current`；
3. 发版检查单新增一项：**`node sync-content.js --ver <新版本>` 必须先跑**；
4. `content/manifest.json` 的 `current` 仅用于后台展示，**不参与授权决策**。

## 10. 安全边界（诚实口径）

| 攻击方式 | 挡得住 | 靠什么 |
|---|---|---|
| 断网继续用 | ✅ | 本地无源，`src/content/` 拿不到就是拿不到 |
| 把内容包拷到别的机器 | ✅ | 换包请求要 `Ke` 签名 `proof`，服务器按 lic 记录的 `ke` 验签 |
| 拷整个游戏目录到别的机器 | ✅ | 新机器 `Ke` 不同 → 换包失败 |
| 自己搭假授权服务器返回内容 | ✅ | `sig` 是 `Ks` 签的；`Ks` 私钥永不出服务器 |
| 把 `grant/` 目录囤起来复用 | ✅ | 启动无条件清 + `exp` 仅 15 分钟 |
| 改系统时间回滚延长 license | ⚠ 部分 | 服务器侧 `ts` ±5min 窗口能挡重放；但 EXE 是本地信任根，改时间骗自己仍可能 |
| **改 `main.js` 跳过检查** | ❌ | asar 不加密，改一行 `if (rel.startsWith('/src/content/'))` 即可 |
| **逆向协议后自建服务器** | ❌ | 客户端方案的物理上限，无解 |

**结论**：本方案把「四类常见规避」全部堵死，足以支撑加盟商 / 街机场景。
**不要把它当作绝对防护**——要再往上，唯一的路是把**关键数值**（刷怪计划、敌人属性）也搬服务器，
而那是下一阶段的事（用户已明确「先做前者、看效果再加码」）。

## 12. 运营影响与应急预案（硬档的代价）

**这是本方案最大的成本，必须提前准备。**

| 风险 | 后果 | 预案 |
|---|---|---|
| 授权服务器宕机 | **所有加盟商门店同时停业** | ① 服务器健康监控 + 告警（`/api/health` 已可用）；② 备份机 + 快速切换文档；③ 私钥备份已双关验收（见 MEMORY） |
| 门店断网 | 该店不能开业 | 装机手册写明「必须联网」；门店需自备 4G 备份线路 |
| 服务器到期/欠费 | 同上 | 日历提醒 |
| 内容同步漏跑 | 全部门店报 `noContentVersion` | 发版检查单强制项（§9） |

**建议同时做的运维配套**（不属于本方案，但强相关）：

1. **容量评估**：N 台机器 × 每次启动 1 次换包。1000 台门店、每天各开关 1 次 ≈ 1000 次/天。
   相对现有 `renew`（每 6 小时一次 = 4000 次/天/千台）**反而更少**，服务器压力不是问题。
2. **激活明细**（当前缺口）：`activations.used_by` 是**覆盖写**（`lib/db.js:99` `SET used_by=?`），
   一个码发 50 台只记最后一个 lic ⇒ 你必须能查「某门店激活了哪几台」。
   建议新增 `activation_log` 明细表（`code, lic, dev, ip, at`）。
3. **批量吊销**：加盟商退出要一键停整个门店。现状只能逐行点（`public/admin.html` license 表按钮），
   需按 `cust` / 激活码批量操作。

## 附 · 2026-09-24：本文档与「服务器清单」的关系（**先读这段再读正文**）

> 需求方 2026-09-24 拍板：**不做加密狗式授权校验**，改成「每次启动从服务器拉一份配置清单」。
> 该方案**已实现**，落地在 `tools/cast-server/server.js` + `tools/cast-server/sync-content.js`
> + `tools/cast-pc/main.js` + `MainActivity.java`，完整口径见
> [`docs/tech/09-服务器清单与旧配置清理.md`](./tech/09-服务器清单与旧配置清理.md)。

### 两句话概括差别

| | **本文档（Content Grant）** | **服务器清单（第二十四修，已实现）** |
|---|---|---|
| 目的 | 防抄袭：内容本地不留源、防拷走 | 配置集中管理 + 版本一致 + 不留旧配置 |
| 鉴权 | 服务器签名 + **绑机**（PoP） | **共享密钥**（`manifestKey`），不绑机 |
| 强度 | 高（私钥不出服务器） | 低（密钥在客户端里，只挡运营事故） |
| 状态 | **设计定稿，待实现** | **已实现，正式包默认开启** |

### 什么被实现了、什么没有

- **已实现（部分等价）**：① 内容不再随安装包走（改为 EXE 每次启动从服务器取）
  ② 配置本地不留旧版本（启动先清 + 本局结束清 + `before-quit` + 头显 `clearOverlayCache`）
  ③ 拿不到服务器内容就**明确失败、绝不回落本地**。这三条与本文档的核心诉求一致。
- **没有实现（本文档独有、且更强）**：① 服务器**签名**（清单是明文 HTTP + 共享密钥，可被抓包重放）
  ② **绑机**（清单可被拷到任意机器使用）③ EXE 侧不落明文源（清单在磁盘上是明文文件）
  ④ `POST /api/content/grant` 那套逐次授权的协议。

### 结论

**别把这两套搞混**：现场跑的是「服务器清单」；如果哪天商业上要求「内容拷走了也用不了」，
再照本文档把**签名 + 绑机**加回去 —— 那时可以把 `/api/manifest` 的响应改成带签名的版本，
而不是推翻重来（`manifestFetch()` 里已有逐个文件的 `sha256` 自校验位，加签名的位置是现成的）。
