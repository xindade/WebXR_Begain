# 平台对接需求（对平台方）

> 立项：2026-09-23　来源：《打包和平台对接》（需求方 7 条）
> 本文只列**需要平台方配合**的事，以及**我们已完成、平台无需改动**的事。
> 实测依据见 `平台指令/`（流量取证 + WebVR 对接探针），非推测。

## 一、部署形态（已定案，不再讨论）

| 项 | 结论 |
|---|---|
| 观众路数 | **单路**（现场一台 PC 大屏），维持 WebRTC P2P，**不引入 SFU** |
| 游戏包 | EXE（PC 直播接收端）+ APK（头显端），共 2 个 |
| 开局信号 | APK 拉起本页时带 `?plat=1`（平台点「开始游戏」在设备侧唯一可见形态） |
| 门禁 | 正式包**硬拦**：必须 PC 主控端明确回「允许运行」 |

## 二、需要平台方配合（按优先级）

### 1. 启动器补 `close game path`（对应需求第 6 条）
- **现状**：平台结束本局时下发字符串 `{"cmd":"kill","msgData":"<进程名>"}` + CMD 16 `CloseGame`，
  然后清掉 P2P 房间数据。实测**只能按进程名 kill**，没有「按 exe 路径 / 游戏目录关闭」的能力。
- **问题**：我们的 APK（头显端）**不是** PC 上的进程，`kill` 打不到它；PC 端 EXE 关掉了，
  头显侧的浏览器/游戏页还活着 → 现象就是「平台说结束了，头显还在跑」。
- **需要平台方**：在启动登记里补一个**可关闭标识**（exe 相对路径或自定义 close path），
  并在 `kill` 时允许按它关闭；或明确给出「关闭 APK / 关闭头显端」的下行通道。
- **我方兜底（已完成，不必等平台）**：PC 端关掉后，头显侧页面看门狗
  （`src/game/game.js` 的 `_onPlatformGone` + 判死复核）会在连败 4 次 ≈6s 后自行收尾并关闭浏览器。
  也就是说**无需平台改动我们也能收场**，只是收敛速度依赖网络抖动。

### 2. 定义「游戏结束」上行报文（对应需求第 7 条）
- **现状**：我们已按 `VRPlatformLib.dll` 的 CMD 表上报 **CMD 5 `GameStart`**（中途结束兜底）
  和页面留痕事件 `game-end`，但**没有**上报过 **CMD 6 `GameEnd`** —— 因为我们不知道它的 payload 结构，
  乱发可能被平台判为非法帧。
- **需要平台方**：给出 CMD 6 `GameEnd`（以及 CMD 7 `GameStatistics` / CMD 17 `GameLevel`）
  的**字段定义与触发时机**（谁负责在「自然结束」时发、必填字段有哪些）。
- **我方兜底（已完成）**：本局自然结束会写入**本地留痕时间线**
  （`game-end` via `/api/page/event` → APK `PageForensics`），现场可离线对账。
  另：APK 侧已有「平台不在场 / 已结束」的检测（`sPlatformDriven` / `isPeerAlive`）。

### 3.（可选）补发「开始游戏」指令（对应需求第 5 条）
- **现状**：整局实测平台**零「开始」下行**（逐帧留痕只有机位表回执 + `0x10 closeGame`，
  没有 cmd3/4、没有 JSON、没有单字节命令，也没有第二次 `am start`）。
- **我方现行判据**：以「本页由 APK/平台拉起（`?plat=1`）」为开局信号，**外加 30 秒无条件兜底**，
  保证现场绝不卡死。
- **需要平台方**：若希望开局时刻**精确**（而不是「拉起即可进」），请补发一条明确的开始指令；
  我们两条判据**并肩**，平台一旦补发即自动生效，无需我方再改。

### 4. 确认 EXE 启动参数格式（对应需求第 4 条）
- **实测格式**（`平台指令/VRPlatform-流量取证/指令速查.md`）：
  ```
  argv[1] = "<exe 相对路径>$<进程名不含 .exe>$<平台本机 IP>"
  例：DeadHospital2-8.0.5\DeadHospital2.exe$DeadHospital2$192.168.31.228
  ```
- **我方已实现**：EXE 能解析上面这个位置参数，并额外接受三个**可选**具名参数
  `--room=<房间号>`、`--platform=<IP:端口>`、`--game=<游戏名>`；
  一个都不给时的行为与现在**完全一致**（自动发现 + 手动配置游戏目录 + 端口 fallback）。
- **需要平台方确认**：登记我们的 EXE 时，游戏目录 / 工作目录（cwd）如何设置；
  以及房间号是否可以从启动参数获得（我们已预留 `--room`，用于留痕对账）。

### 5. 包标识与签名（影响后续升级）
- PC 端 EXE：`appId = com.local.webxrcast`（`tools/cast-pc/package.json`）。
- 头显端 APK：`applicationId` 见 `tools/cast-apk/app/build.gradle`。
- **约束**：`applicationId` **必须与平台登记一致**；**签名变更会影响平台侧升级**（安装时校验不过会拒绝覆盖）。
  本轮不做代码签名与版本号流程改造，仅在此记录。

### 6. 网络与端口（现场开箱检查用）
| 用途 | 端口 / 地址 |
|---|---|
| PC 接收端 HTTP（静态托管 + 信令 + 帧） | TCP **8443**，被占用时自动 +1 重试至 **8453** |
| 局域网发现信标（PC → 头显） | UDP 组播 **224.0.0.100:8444**，每 2s 一条 `WEBXR-CAST:<端口>` |
| 头显 APK 本地游戏服务 | TCP **8080**（`/api/*` 代理到 PC） |
| WebRTC 媒体 | 由 ICE 自行协商（host candidate，局域网直连） |
- **需要平台方**：确认上述端口在平台/现场网络策略里未被占用或拦截；组播 224.0.0.100 不被 AP 隔离
  （有 AP 隔离的场地，头显发现不到 PC，只能人工在 APK 配置页填地址）。

### 7. CMD 表版本差异 / 加密通信
- 实测提示：CMD 表**随 SDK 版本变化**；日志里出现过**加密通信启动游戏**的痕迹。
- **需要平台方**：给出我方对接使用的 **SDK 版本号**，以及「哪些下行帧可能是加密的」。
  若开局/结束指令可能加密，请一并给出解密约定，否则我们只能继续用「拉起即开局」+ 本地兜底。

## 四、现场验收清单（与平台联调时逐条打勾）

1. 平台上点「启动」→ PC EXE 起来（界面顶部显示平台参数）、头显 APK 进等待界面。
2. 门禁三态：正式包 + PC 未放行 → 头显停「需要主控端启动」页（附 PC 地址 + 重试）；
   正式包 + PC 放行 → 正常进 VR；调试包 / 网址 `?gate=0` → 放行。
3. 直连兜底路径 `http://<PC>:8443/?cast=1` **不受门禁影响**，仍能独立诊断画面。
4. 点「开始游戏」→ 头显出现「进入 VR」；点进 VR → PC 大屏播本地开场影片（**有声音**）。
5. 影片期间**不推流也不推音频**；影片结束后 PC 切回头显实时画面 + BGM/音效。
6. 点「结束游戏」→ PC EXE 关闭；头显侧在 ≈6s 内自行收尾并关闭浏览器。
7. 异常路径：拔网线 / 关 PC → 头显不软锁，按兜底收场。
