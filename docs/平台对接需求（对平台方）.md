## 一、部署形态（已定案，不再讨论）

| 项 | 结论 |
|---|---|
| 观众路数 | **单路**（现场一台 PC 大屏），维持 WebRTC P2P，**不引入 SFU** |
| 游戏包 | EXE（PC 直播接收端）+ APK（头显端），共 2 个 |
| 开局信号 | 平台是**两步**：① **「启动游戏」**= 启动器 `{"cmd":"start"}` 拉起 PC EXE + 头显里的游戏（**此时不放行**）；② **「开始游戏」**= 游戏通道 **CMD 5 GameStart**（UDP 51124）⇒ PC 端 `roundSet(true)`、头显 APK 收 `0x05` 转 `cmd 21` 开门禁 ⇒ 页面出现「进入 VR」。`?plat=1` 与「EXE 被平台拉起」**都不是**开局判据（抓包逐帧见 `docs/cast-architecture.md` 附录 D） |
| 门禁 | 正式包**硬拦**：必须 PC 主控端明确回「允许运行」 |

## 二、需要平台方配合（按优先级）

### 1. 启动器补 `close game path`（对应需求第 6 条）
- **现状**：平台结束本局时下发字符串 `{"cmd":"kill","msgData":"<进程名>"}` + CMD 16 `CloseGame`，
  然后清掉 P2P 房间数据。实测**只能按进程名 kill**，没有「按 exe 路径 / 游戏目录关闭」的能力。
- **问题**：我们的 APK（头显端）**不是** PC 上的进程，`kill` 打不到它；PC 端 EXE 关掉了，
  头显侧的浏览器/游戏页还活着 → 现象就是「平台说结束了，头显还在跑」。
- **需要平台方**：在启动登记里补一个**可关闭标识**（exe 相对路径或自定义 close path），
  并在 `kill` 时允许按它关闭；或明确给出「关闭 APK / 关闭头显端」的下行通道。
- **我方兜底（已完成，不必等平台）**：PC 端关掉后，头显侧页面看门狗
  （`src/game/game.js` 的 `_onPlatformGone` + 判死复核）会在连败 4 次 ≈6s 后自行收尾并关闭浏览器。
  也就是说**无需平台改动我们也能收场**，只是收敛速度依赖网络抖动。

### 2. 「游戏结束」上行报文：**已实测破解、我方已接入（CMD 7）、现场验证通过** —— 只剩一个字段语义待确认（对应需求第 7 条）

- **★ 2026-09-24 现场实测结案**：平台的「游戏结束」信号是 **CMD 7 `GameStatistics`**，
  **不是** CMD 6 `GameEnd`（整场采集里 CMD 6 **从未出现**）。证据来自现场一局采集
  （`tools\collect-round.bat` → `E:\AI_Work\WebXR_Capture\20260924-175353\`）：
  18:10:20 本机 → 平台 `0x07` + **397 字节 UTF-8 JSON**（无长度前缀、无结尾符）；
  平台 `DebugLog` 同一秒 `===ReceiveCall==…cmd = 7` → `OnReceiveResultMsg` → `==PostGameResult==`
  → `游戏计时已暂停` → **`游戏结束 场次ID:15 结算类型:正常结算`**，且平台**不会**因此关游戏
  （实测那次 kill 是 82 秒之后、由人点「结束游戏」触发的）。
  ⇒ 这正是「告知平台本局结束、但别关游戏」的正解。
- **我方已接入（已完成，不必等平台）**：`tools/cast-pc/main.js` §平台游戏通道 —— 用注册时的**同一个
  socket**（源端口 51124）向 `<平台IP>:51234` 发 `0x07`；载荷字段逐字照抄原版实测样本，
  并**已与抓包字节逐字节比对通过**（397 字节全等，见 `docs/tech/05-游戏打包方式（EXE与APK）.md`）。
  触发点 = 本局自然结束（页面 `POST /api/round/end`）；开关 `--no-game-result`（默认开）；
  现场自测端点 `POST /api/platform/game-result` —— **不用打满一整局**就能验平台会不会弹结算。
  ★ **2026-09-24 现场验证通过**：装上新 EXE 后，平台界面**立刻出现结算按钮**、且**不关游戏**
  —— 也就是「只告知本局结束、但别关游戏」这条已跑通。（第一次失败的原因见下面第 4 点。）
- **只此一项需要平台方回答**：`result` 字段的**取值语义**（0 / 1 / 2 分别代表什么？通关 / 失败 / 中途退出？）。
  原版那一局发的也是 `0`、平台记成「正常结算」⇒ 我方默认一律发 `0`；若平台要区分，请给对照表。
- **另外两点已实测确认无需平台改动**：① `gameid` / `instid` / `shopid` 原版也全发 `0`，
  平台按本局会话自行补成 `128 / 15 / 1`；② `gameData` 必须是**字符串化的 JSON**（不是嵌套对象），
  平台**原样透传**。
- **我方兜底（已完成）**：本局自然结束同时写入**本地留痕时间线**（`game-end` via `/api/page/event`
  → APK `PageForensics`），现场可离线对账。另：APK 侧已有「平台不在场 / 已结束」的检测
  （`sPlatformDriven` / `isPeerAlive`）。

### 4. ★ 排障要点：上行帧的**源 IP** 必须是本机网卡地址，不能是回环（2026-09-24 现场定案）

第一次现场轻量验证报 `ok: true / results: 1`、PC 端确实发了 397 字节，平台却毫无反应。根因是
**目标地址选成了 `127.0.0.1`** ⇒ 内核把源地址也选成回环 ⇒ 平台按「外来 IP」丢弃。

现在 PC 端按 ① 平台来帧的源 IP ② 启动参数 ③ 本机默认路由网卡地址 取**一个**，**绝不用回环**。
这一条**不需要平台配合**，仅记录现场坑：异步发帧（没有收到帧时的主动上报）必须能回答「目标从哪来」。

### 3. 开局指令：**已结案，不需要平台改**（对应需求第 5 条，2026-09-23 晚 · 第二十修）
- **实测已拿到开局帧**：平台点「开始游戏」时下发游戏通道 **CMD 5 GameStart**（UDP 51124，
  `\x05{"difficulty":0,…,"gameId":128,…}`）。我方已**完整接入**：
  PC 端监听 51124 并回 118 字节确认帧；头显 APK 收 `0x05` 转 `cmd 21` 开门禁。
  见 `docs/cast-architecture.md` 附录 D。
- **需要平台方配合的点（小）**：保证这一步**照常下发到 PC 的 UDP 51124**。抓包显示该帧
  **只发给了跑游戏的那台机器**，头显没收到 —— 我们靠 PC 的 `POST /api/round/start` 回报兜底。
  若平台愿意**同帧也给头显侧发一份**，收敛会更快（可选，非必需）。
- **仅当**平台希望「同一个 EXE 实例内连续开多局、中途不重启进程」时，才需要额外补发
  「开始本局 / 结束本局」下行指令；接口已就绪（PC 的 `roundSet()`）。当前「一局一拉进程」形态下**无需平台改动**。

### 4. 确认 EXE 启动参数格式（对应需求第 4 条）
- **实测格式**（`平台指令/VRPlatform-流量取证/指令速查.md`）：
  ```
  argv[1] = "<exe 相对路径>$<进程名不含 .exe>$<平台本机 IP>"
  例：DeadHospital2-8.0.5\DeadHospital2.exe$DeadHospital2$192.168.31.228
  ```
- **我方已实现**：EXE 能解析上面这个位置参数，并额外接受三个**可选**具名参数
  `--room=<房间号>`、`--platform=<IP:端口>`、`--game=<游戏名>`；
  一个都不给时的行为与现在**完全一致**（自动发现 + 手动配置游戏目录 + 端口 fallback）。
- **需要平台方确认**：登记我们的 EXE 时，游戏目录 / 工作目录（cwd）如何设置；
  以及房间号是否可以从启动参数获得（我们已预留 `--room`，用于留痕对账）。

### 5. 包标识与签名（影响后续升级）
- PC 端 EXE：`appId = com.local.webxrcast`（`tools/cast-pc/package.json`）。
- 头显端 APK：`applicationId` 见 `tools/cast-apk/app/build.gradle`。
- **约束**：`applicationId` **必须与平台登记一致**；**签名变更会影响平台侧升级**（安装时校验不过会拒绝覆盖）。
  本轮不做代码签名与版本号流程改造，仅在此记录。

### 6. 网络与端口（现场开箱检查用）
| 用途 | 端口 / 地址 |
|---|---|
| PC 接收端 HTTP（静态托管 + 信令 + 帧） | TCP **8443**，被占用时自动 +1 重试至 **8453** |
| 局域网发现信标（PC → 头显） | UDP 组播 **224.0.0.100:8444**，每 2s 一条 `WEBXR-CAST:<端口>` |
| 头显 APK 本地游戏服务 | TCP **8080**（`/api/*` 代理到 PC） |
| WebRTC 媒体 | 由 ICE 自行协商（host candidate，局域网直连） |
- **需要平台方**：确认上述端口在平台/现场网络策略里未被占用或拦截；组播 224.0.0.100 不被 AP 隔离
  （有 AP 隔离的场地，头显发现不到 PC，只能人工在 APK 配置页填地址）。

### 7. CMD 表版本差异 / 加密通信
- 实测提示：CMD 表**随 SDK 版本变化**；日志里出现过**加密通信启动游戏**的痕迹。
- **需要平台方**：给出我方对接使用的 **SDK 版本号**，以及「哪些下行帧可能是加密的」。
  若开局/结束指令可能加密，请一并给出解密约定 —— 否则我们可能漏收第 ② 步的 GameStart，
  届时只能退回「PC 主控端手动点『开始本局』」的排练路径。

### 8. ★ 请停止「每 20s 重发一次整套启动」（2026-09-24 现场实测，优先级高）

**现象**：平台客户端每 **20.004s** 重发一次整套「启动游戏」——
`kill`（`am force-stop com.GoodNet.DeepmindHacker`）→ `copyfile(setup.xml)` →
`am start -n com.GoodNet.DeepmindHacker/.MainActivity -d <PC_IP>`。
现场表现为「头显客户端启动了两次游戏，中间隔 20 秒左右」。

**后果（本场最贵的一条）**：第二次 `am start` 时玩家往往**已经在 VR 里**。
此时只要有任何「2D 应用想占前台」，PICO 的 XRShell 就弹系统弹窗
「**退出PICO浏览器** / 你需要退出当前应用才能继续操作」，并**当场挤掉 XR 沉浸式会话**
（本局作废，玩家被弹出 VR）。2026-09-24 现场实测复现。

**我方已做的兜底（第二十六修，2026-09-24）**：
① 头显侧在「本局仍在跑」时**绝不产生窗口、绝不发任何前台动作**；
② 页面的判死复核从 1 轮改成 2 轮，避免撞上 APK 重启的那几秒被误判成「游戏已死」。
细节见 `docs/cast-architecture.md` 附录 F 与 `docs/cast-implementation-and-packaging.md` 附录 G.9。

**我方第二轮兜底（第二十七修，2026-09-24，只重打了 APK）**：实测证明「不建窗口」还不够 ——
只要我们的 Activity 被创建（哪怕 NoDisplay + 立刻 finish），PICO 也会给它建 2D 面板并顶掉 XR 会话
（同一局留痕：14:02:18.241 `只 finish 本页` → 14:02:18.330 `xr-end`，相隔 **89ms**）。
故本版在**本局处于 VR 会话期间把「平台入口」组件（`…/.MainActivity`）临时停用** ——
平台那一次 `am start` 会在包管理器层被拒（不产生面板 / 闪屏 / 弹窗），退出 VR 或本局结束立即恢复；
另有死人开关（60s）、页面打点停止、进程启动、开机、覆盖安装、人工恢复入口共 7 道恢复网
（实现与验收见 `docs/cast-architecture.md` 附录 G）。

**我方第三轮兜底（第二十八修，2026-09-24，只重打了 APK）**：第二十七修上线后现场**仍然弹窗** ——
留痕显示平台在被 `-n …/.MainActivity` 拒掉后会**退化成隐式 MAIN/LAUNCHER**（或 `getLaunchIntentForPackage`），
解析到了我们当时唯一启用的「恢复入口」Activity：14:59:17.418 命中该 Activity → 14:59:17.618 `xr-end`
（相隔 **200ms**，本局又被挤出 VR）。故本版把不变式收紧为
「**本局在 VR 会话里 ⇔ 包内 MAIN/LAUNCHER 入口数 = 0**」——入口与恢复入口**同时停用**，
平台那一次启动会**解析失败**（见下面第 4 条）。除「平台客户端自己抢前台」这一种我们无法处置的情形外，
客户端侧已不存在任何可被平台拉起的窗口，弹窗链路在游戏侧闭合。

**需要平台方**（三条，按重要性）：
1. **启动成功后停止重发**：收到游戏通道 `0x01`（我们在 `am start` 后 57ms 内就会发）或启动器回执后，
   不要再用 `am start` 重发整套；若必须保活，请把周期放到分钟级并改用**不改变前台**的动作。
2. **游戏运行期间客户端不要抢前台**：若「想占前台的那个 2D 应用」是客户端自己，
   则我方**无从修复**（我们只能保证不产生自己的窗口）。检测到沉浸式会话时请勿前置。
3. **不要带 `kill`**：`am force-stop` 会杀掉我们的本地服务（头显 `localhost:8080`）与页面心跳，
   是「第二次启动」破坏链的第一环；确实需要重启时，请只在**游戏已结束**后发。
4. **启动命令请用「显式组件」**：即 `am start … -n <包名>/<完整类名>`（我们入口的完整类名是
   `com.GoodNet.DeepmindHacker/com.local.webxrcast.MainActivity`）。
   若用的是不带 `-n` 的隐式 intent（只给 `-a MAIN -c LAUNCHER`）或客户端直接调 `getLaunchIntentForPackage`：
   第二十八修起，我们在**本局处于 VR 会话期间会把包内所有 MAIN/LAUNCHER 入口（含恢复入口）全部停用**，
   于是你那一次启动会**直接失败** —— shell 版报
   `Error: Activity not started, unable to resolve Intent`，应用内 `startActivity` 抛
   `ActivityNotFoundException`。**请对这次失败做容错**（不要弹错误框、更不要因此崩 UI），
   并按上面第 1 条在收到回执后停止重发。

## 四、现场验收清单（与平台联调时逐条打勾）

1. 平台点「**启动游戏**」→ PC EXE 起来（界面顶部显示平台参数、日志出现「本次由平台「启动游戏」拉起（第一步）」）、
   头显 APK 起来并进游戏页；**此时头显不出现「进入 VR」**，应显示「⏳ 等待平台点「开始游戏」…」。
2. 平台点「**开始游戏**」→ 头显出现**二选一按钮**（蓝 `⚡ 射速加倍 · 攻击力减半` / 红 `💥 攻击力加倍 · 射速减半`）；
   点任一个都直接进 VR，并按对应倍率改本局初始属性（蓝：攻击力 100→50、射速 2→4 发/秒；
   红：攻击力 100→200、射速 2→1 发/秒；后续抽卡/死亡加成照旧在其之上叠加）。
   PC 侧 `http://127.0.0.1:<端口>/api/info` 应看到 `round.armed=true`、`gameChannel.lastStartFrom` 有值、
   `gameChannel.machines ≥ 1`（后者 = 平台已认到本机注册）。
3. 门禁三态：正式包 + PC 未放行 → 「⏳ 等待平台点「开始游戏」…」；拿到放行 → 正常进 VR；
   调试包 / 网址 `?gate=0` → 放行。
4. ~~直连兜底路径（头显浏览器直连整站）~~ **已于本轮停用**（档1）：PC 端不再托管游戏整站，
   打开 `http://<PC>:8443/` 只会看到一段说明性 404。诊断改看 `GET /api/info`（`panels` / `extCfg` /
   `gameChannel.bound`）与 EXE 窗口日志。
5. 点进 VR → PC 大屏播本地开场影片（**有声音**）；影片期间**不推流也不推音频**；
   影片结束后 PC 切回头显实时画面 + BGM/音效。
