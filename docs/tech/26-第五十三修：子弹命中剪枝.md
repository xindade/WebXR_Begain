# 第五十三修：子弹命中剪枝（`_collide` 的「第 0 步」）

## 0. 为什么做

现场口径：「**要更多子弹**」，并且对四个追问的答复是 —— 追踪算**道具**（不是技能卡）、
**接受部分子弹追踪**、**目前还没掉帧**（只是后期有这个打算）。

把这条需求拆开看，三个闸门里前两个都只是**改数字**：

| 闸门 | 位置 | 现值 |
| --- | --- | --- |
| 多重弹道 | `src/content/cards.js` → `ATTRIBUTE_STATS.multiShot` | 上限 7（**已由第五十四修放开到 12**） |
| 射速 | `src/content/cards.js` → `ATTRIBUTE_STATS.fireRate` | 上限 14 发/秒（**已由第五十四修放开到 20**） |
| 并发子弹数 | `src/core/constants.js` → `SHOOT.BULLET_POOL_SIZE` | 500（**已由第五十四修提到 1000**） |

并发子弹数 ≈ 射速 × 弹道数 × `SHOOT.BULLET_LIFE`(2s)：现在 14 × 7 × 2 = **196**，池子 500 还剩一半余量。
渲染侧几乎免费 —— `src/game/bullets.js` 是 `InstancedMesh`，1000 发也只是 1 个 draw call +
一次 32KB 矩阵上传。

真正的门槛在**命中判定**：`game._collide()` 是 O(子弹 × 敌人 × 2 pass)，每个 pair 都要算一次
「点到本帧线段最近点」，立绘（`depthSprite`）那条分支还多一次 `normalize()`
（`sqrt` + 三次除法）。所以先把这里的地基垫平，再谈放数值。

## 1. 改了什么（两处，都**不改变命中结果**）

### ① 场上没有 Boss 时只跑一轮

`pass0`（只判非 Boss 目标）/ `pass1`（只判 Boss 代理）这两轮是第四十修加的：
Boss 代理的命中球半径 4m，且常待在「九宫格球 / 精英」的正后方，按 `list` 顺序优先判定就会
**抢走**本应命中前方目标的子弹（表现为「打小怪掉 Boss 血」）。

但 `pass1` 只在有 Boss 的关卡才有意义 —— 非 Boss 关它每帧都是**纯空转**。
现在 `_collide()` 开头先扫一次 `balloons.list`，没有「存活且 `isBoss`」的怪就把 `passCount` 压到 1。

> 为什么扫一次就安全：`_collide()` 这条路径上**没有任何地方生成 Boss**
> （`isBoss` 只在 `waves.js` 的 `_queueSpawn` / `bossMagician._spawnProxy` 里赋值），
> 所以一帧之内「有没有 Boss」不会中途翻转。Boss 被打死那一帧也没关系 —— 它已经被
> `balloons.remove()` splice 出表了，`pass1` 本来也找不到它。

### ② 每个 pair 先过一道「本帧线段 AABB」粗筛

子弹本帧的轨迹是一个**直线段** `prevPos → pos`，它的包围盒就是两端点逐分量取 `min/max`
（每发子弹 6 次比较，一次算好）。于是每个 pair 先做 6 次比较：

```js
const bpos = balloon.mesh.position;
const pad  = balloon.depthSprite ? rr + SHOOT.HIT_SLAB_DEPTH : rr;
if (bpos.x < segMinX - pad || bpos.x > segMaxX + pad) continue;
if (bpos.y < segMinY - pad || bpos.y > segMaxY + pad) continue;
if (bpos.z < segMinZ - pad || bpos.z > segMaxZ + pad) continue;
```

粗筛是**保守**的（不可能漏判）：`线段 ⊆ 线段 AABB` ⇒
「点到线段的距离 ≥ 点到线段 AABB 的距离」⇒ 出盒必然打不中。反向也成立：只要真的命中，
点离线段就小于命中半径，也就必然落在「AABB 外扩半径」的盒子里。

垫厚分两种口径：

- 普通怪：命中条件是「点到线段距离 < rr」⇒ 垫 `rr` 就够；
- 立绘薄板：命中条件是「**平面内**分量 < rr **且** 纵深分量 < `HIT_SLAB_DEPTH`」，
  两点合成后 `点到线段距离² = 平面内² + 纵深² < rr² + 板厚²` ⇒ 必须垫 `rr + 板厚`（`rr + HIT_SLAB_DEPTH`）。
  ⚠ 这一条是**真正的坑**：只垫 `rr` 会把「横向 0.5 / 纵深 0.37」这类**合法命中**判成假阴性
  （点到线段距离 0.622 > rr 0.55，但它确实是命中）—— `tests/collide-prune.test.mjs` 里有专门一条锁它。

省下的是精确判定里最贵的部分：`_closestPointOnSeg` + `_segAB/_segN` 的向量运算，
以及立绘分支的 `normalize()`（`sqrt` + 三次除法）。遍历顺序与「非 Boss 优先」的优先级
**原样保留**，所以命中对象、命中顺序与改前逐条一致。

## 2. 怎么保证「零行为变化」

`tests/collide-prune.test.mjs`（10 项）把**改动之前的 `_collide` 原样抄成本文件里的 oracle**，
同一批场景下要求新旧两边的轨迹（命中对象 / 扣血量 / 击杀 / 子弹消费顺序 / 末尾 `sync`）逐条一致：

- **600 组随机场景**（含 Boss / 立绘 / 薄血条口径 0.2 / 死怪 / 隐身幽灵 / 盾兵 / `revealed=false`），
  其中 >300 组真的打中过 —— 防止「两边都没命中」的空转把等价性蒙过去；
- 定点用例：命中球边界内外（`rr ± 0.01`）、退化线段（首帧 `prevPos === pos`）、
  立绘薄板「离线段比 rr 远、但纵深在板厚内」、玻璃墙拦截、盾兵挡弹与背身、
  无 Boss 只跑一轮（用 `alive` 读取数精确断言 `2NM → NM + M`）、远场零 `normalize`（`Math.sqrt` 计数）。

> ⚠ oracle 是**冻结副本**：日后若有意改动精确判定（板厚、命中球口径、优先级…），
> 必须同步重新抄一份，否则这份测试会拿旧口径把新行为判成「不一致」。

## 3. 实测（Node 微基准，60 帧均值、同种子、本机 dev CPU）

| 场景 | 改前 | 改后 | 提速 |
| --- | --- | --- | --- |
| 现状 · 196 发 × 40 怪 | 0.335 ms | 0.180 ms | ×1.86 |
| 扩容 1 档 · 480 发 × 50 怪 | 0.684 ms | 0.260 ms | ×2.62 |
| 池上限 · 1000 发 × 60 怪 | 1.948 ms | 0.557 ms | ×3.50 |

越密收益越大（粗筛剔掉的比例越高）。头显 CPU 比 dev 机慢，绝对值要乘几倍 ——
但 72fps 的预算是 13.9ms/帧，`_collide` 现在在**最极端**的 1000 发 × 60 怪下也不到 1ms（本机）。

## 4. 没做什么

- **数值一个字没动**（弹道 7 / 射速 14 / 池 500 / 曳光池 512 全部维持原样）—— 那是「第 1 步」，
  等用户确认口径后再改（注意 `FX.TRACER.CAPACITY 512` 与子弹池是联动的）。
- **遍历顺序仍是生成顺序**，不是「由近到远」。所以「怪堆里子弹可能打穿前面的怪命中后面那只」
  这个已知缺陷**没有**在这一修里动 —— 那会改变命中结果（玩法侧决定），不能混进「零行为变化」里。
- 追踪道具（「第 2 步」）未开始。
