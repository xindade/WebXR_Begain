## 0. 一句话结论

1. **神掌翻面**：第四十三修的判据（`法线 · 指向相机 < 0`）在现场几何下**永远不会成立** ——
   掌图沿 `y=0` 飞、相机在 `y≈1.6`，「指向相机」长期偏 `+Y`，平滑帧步长（1 秒飞 60m ≈ 0.83m/帧）
   下相邻两帧方向夹角不到 4°，点积恒 > 0.8 ⇒ 闩锁从不触发 ⇒ 掌图越过玩家后继续每帧朝相机，
   从「竖直接着玩家」一路**仰面转到 ~180°**（现场看到的「翻一下」就是这个）。
   新判据：**看掌图中心沿飞行轴是否已越过玩家**（与视线、头转无关），越过那一刻**一次性闩锁**。
2. **连杀计数**：不再往枪身加任何东西 —— 改画在**右手技能框的画布上**：沿边框**等距 10 个方块** +
   右下角「杀敌 N/10」（画在最后 = 最上层）。枪身那条红点环**默认关闭**（实现与参数全部保留，
   `RAPID_FIRE.COUNTER.BARREL_DOTS: true` 即恢复），枪身只留「加速期间向后飘的雾」。
3. **开场黑边**：交接那一帧才第一次做「全景 JPG 解码（`sky-01.jpg` 0.5MB → 解压 4K×2K ≈ 33MB）+ `initTexture`(GPU 上传) + 穹顶材质编译」，
   一帧拉长几十~几百 ms ⇒ WebXR 合成器补不出这么长的位移 ⇒ 视野边缘露出未重投影的黑边（转头最明显）。
   现在把这套重活**提前到影片播放期间**做完（那时天空本来就被 `setIntroBackdrop(true)` 藏着）。
4. **按设备下发参数**：链路本来就通了（`AIM.BY_DEVICE` 四槽 + 运行时设备判定 + `userConfig.js` 下发），
   本修补上 **PC 侧改法**：`node tools/set-aim.js quest 14 -14 0` —— 改的是 `userConfig.js`，
   由直播端自动下发给头显，**头显一个字都不用敲**，也不用重打 APK。

## 1. 如来神掌越过玩家后不再翻面

### 1.1 第四十三修的判据为什么形同虚设

第四十三修写的是：

```js
_faceNow.set(0, 0, 1).applyQuaternion(mesh.quaternion);   // 当前法线
if (_faceNow.dot(_faceTmp) < 0) return;                   // 已越过玩家 → 冻结
```

`_faceTmp` 是「掌图 → 相机」的单位方向。直觉上「越过玩家」= 方向掉头 = 点积变负。
问题在于 **相机不在掌图的飞行线上**：掌图沿 `y=0` 从 `z=-30` 飞到 `z=+30`，而相机在 `y≈1.6`（玩家头高）。
把这个方向画出来（相机固定 `(0, 1.6, 0)`）：

| 掌图 z | 「掌图→相机」方向 | 相对起点的总转角 | **与上一帧方向**的点积 |
|---|---|---|---|
| −30 | (0, 0.05, **+1.00**) | 0° | — |
| −0.5 | (0, 0.95, +0.30) | 71° | ≈ +0.87 |
| +0.5 | (0, 0.95, −0.30) | 109° | ≈ +0.82 |
| +30 | (0, 0.05, **−1.00**) | 174° | ≈ +1.00 |

- **相邻两帧**（1 秒飞 60m ⇒ 每帧 ≈ 0.83m）方向变化极小 ⇒ 点积永远 > 0.8 ⇒ **冻结条件从不满足**。
- 于是「每帧朝相机」一直生效：掌图一边飞一边仰面转身，**总共转了 174°** —— 现场看到的就是「翻一下」。
- 判据失效的本质：**相邻帧的点积只能看出「急转弯」，看不出「已经跑到我背后了」**。

而第四十三修的单测之所以「通过」，是因为测试里把相机放在了 `(0, 0, 0)`、掌图和相机同一条 `y=0` 线上：
那种几何下方向真的会掉头、点积真的会变负。**测试的几何和现场的几何不是一回事** —— 这是本条最贵的教训。

### 1.2 现在的判据：沿飞行轴越过玩家

```js
// buddhaFx.faceCamera(mesh, camera, travelDir)
if (travelDir) {
  passed = _travelTmp.subVectors(mesh.position, camera.position).dot(travelDir) > 0;
}
if (passed) { ud[LATCH_KEY] = true; return; }      // 一次性闩锁
```

`travelDir = normalize(END_POS − START_POS)`（默认就是 `(0,0,1)`）。
「掌图中心 − 相机」在飞行轴上的投影 `> 0` ⇒ 掌图已经跑到玩家背后（沿它自己的飞行方向）。
这个判据：

- **与视线/头转无关**（不会因为玩家扭头而误判）；
- **与掌图当前姿态无关**（不会自己把自己锁死）；
- 越过那一帧就永久闩锁 ⇒ 之后无论相机怎么动、掌图怎么飞，朝向都不再变（看到的是掌的背面/底面）。

留了兼容分支：**没传 `travelDir` 时**退回旧的「方向点积」判据（`BUDDHA.LATCH_FACING=false` 时全部退回旧行为）。

### 1.3 闩锁为什么记在 `mesh.userData` 上

`BuddhaFx` 每次释放（`game._updateBuddhaFx` 里 `new BuddhaFx(...)`）都会在 `_build()` 里**新建一个 mesh**，
所以把闩锁写在 `mesh.userData.__budFaceLatched` 上，新一掌天然复位、不需要任何手工清理；
也避免了「实例字段忘了重置 ⇒ 第二掌永远不朝相机」这类脏状态。

## 2. 连杀计数搬到技能框边缘

### 2.1 需求与做法

现场反馈「红点绕着枪还是有点遮挡」→ 改成**技能框边缘的方块**：一共 10 个、沿边框等距，
外加**框内最上层**的杀敌计数。

| 元素 | 位置 | 画法 |
|---|---|---|
| 10 个方块 | **技能框边框线上**（距画布四边 `INSET` 像素的矩形） | 已点亮 = `COLOR`（红）/ 加速期新攒的 = `BOOST_COLOR`（金）实心方块；未点亮 = 小一号的 `EMPTY_COLOR` 暗块（保留空槽，便于数还剩几个）|
| 整圈闪光 | 同一批方块 | 集齐那一瞬（= 新一次加速开始）放大 1.25 倍 + 变 `FLASH_COLOR`（白），`FLASH_TIME` 秒后自己收掉 |
| 杀敌计数 | 框内**右下角** | `杀敌 N/10`（加速期第二行 `加速 2.1s`）；**最后画** ⇒ 永远压在面板最上层 |
| 加速雾气 | 枪身周围（不在面板上） | 仍由 `src/vr/streakCounter.js` 负责，没动 |

### 2.2 沿边框等距怎么算（`edgeDotPositions`，纯函数）

```js
边框 = 距画布四边 inset 像素的矩形（512×320 的画布 + inset 13 ⇒ 486×294，周长 1560）
第 i 个方块的弧长 = ((i + PHASE) / n) * 周长      // PHASE = 0.5 ⇒ 首尾都不落在四角
弧长 → (哪条边, 边内比例) → 平面坐标
```

`PHASE=0.5` 让方块**两两分开、四角留白**：顶边 3 颗、左右各 2 颗、底边 3 颗。
`inset=13` 时方块中心正好压在边框线上（方块边长 26 ⇒ 外侧贴到画布边缘、内侧不侵入正文区）。
抽成纯函数是为了能单测：测试断言「每颗都在边框线上」「沿周长严格等距」「不落在四角」「不切出画面」。

### 2.3 为什么画在同一张画布上，而不是做成新的 3D 物件

- 技能框本来就是**每帧重绘**的 canvas（`SkillHintPanel.update` → `_draw`），
  往同一张画布上多画 10 个 `fillRect` + 一行字**不增加任何纹理上传次数**（`needsUpdate` 反正每帧置一次）；
- 方块与面板天然同坐标系、同朝向、同缩放 ⇒ 不会再出现「贴在枪上位置算错」的问题；
- 面板 `renderOrder = 1000`、`depthTest: false` ⇒ 它本来就压在所有东西最上层，方块跟着它也就不会挡准星以外的画面。

### 2.4 枪身红点环去哪了

**没删。** `RAPID_FIRE.COUNTER.BARREL_DOTS` 新增开关，默认 `false`：

```js
if (C.BARREL_DOTS === false) {          // 第四十四修：默认不画枪身环
  this._fill = Math.min(streak, need);
  this._boost = boost;
  this.dots.visible = false;
  this._updateMist(dt, boost);          // 雾气照旧
  return;
}
```

现场觉得「还是想枪身上也有」，把这一行改成 `true` 即可（与面板同时显示也不冲突）。

## 3. 开场影片播完「转头瞬间黑边 / 卡顿」

### 3.1 现象与根因

现象：影片播完、画面切进第 1 关的那一下，**转头**会看到视野边缘黑边 + 一次明显卡顿。

根因不是「渲染错了」，而是**一帧太长**：

```
onDone → holdLastFrame → HANDOFF_DELAY_S(0.08s) → _commitIntroToLevel()
   → setIntroBackdrop(false) → _loadLevel(0)
      → world.setSkyPanorama(第1关全景)        ← 这里第一次做重活
           · 全景 JPG 的下载 / 解码（第 1 关 sky-01.jpg：0.52MB → 解压 4K×2K ≈ 33MB）
           · renderer.initTexture()：GPU 上传（几十 MB）
           · 新建穹顶几何 + 材质 ⇒ 首次渲染时还要编译着色器
```

一帧拉到几十~几百毫秒 ⇒ WebXR 合成器**补不出这么长的位移** ⇒ 露出的就是未重投影的黑边。
转头时最明显（位移最大）。第 1 关恰好是**有全景的关卡**，而它是「刚进游戏的第一帧」，此前从未加载过。

### 3.2 `world.warmSkyPano(url, camera)` 提前做三件事

在 `game._startIntroVideo()` 里（影片刚开始播、天空已被 `setIntroBackdrop(true)` 隐藏）就调用：

| 步 | 做什么 | 收益 |
|---|---|---|
| ① | `prepareSkyPano(url)` | 下载 + 解码 + `initTexture` 上传，并留下 `_gpuReady` 标记 ⇒ 之后 `setSkyPanorama` 命中「已缓存且已 `_gpuReady`」分支，**同步套用**，不再等待 |
| ② | `_ensureSkydome()` + 挂上贴图 | 穹顶网格与材质提前建好（保持 `visible=false`，不动可见性） |
| ③ | `_compileMaterialOf(dome, camera)` | 把穹顶材质的**着色器程序编出来**，避免首帧编译卡顿 |

预热失败（离线 / 坏图）直接 `catch` 掉，不影响开场：切关时仍走 `setSkyPanorama` 原来的异步兜底。

### 3.3 为什么只编译「穹顶那一个材质」

`renderer.compile(scene, camera, targetScene)` 对**材质**用的是 `scene.traverse(...)`（**不看 visible**），
所以不需要把穹顶真的显示出来；但它会把传进去的那个 `scene` 里**所有**材质都过一遍 ——
如果在影片期间对整个游戏场景调一次，那本身就会卡一帧。

做法：准备一个「探针小场景」只放一个 `Mesh`，把穹顶的 geometry/material 挂上去再 `compile`：

```js
this._warmProbe.geometry = object.geometry;
this._warmProbe.material = object.material;
this.renderer.compile(this._warmScene, cam, this.scene);   // 第三参 = 真场景（取它的 renderState/灯光）
```

`targetScene` 必须传真场景：`compile` 内部 `renderStates.get(targetScene)` 用的是**那个场景的**渲染状态。

## 4. 瞄准角按设备下发（PC 上改，头显零输入）

### 4.1 链路（本修没改协议，只补了操作入口）

```
PC 上编辑 <游戏目录>\src\core\userConfig.js 的 AIM.BY_DEVICE.<槽>
        │   （EXE 的 CONFIG_MANIFEST = ['src/content/', 'src/core/userConfig.js']）
        ▼
平台点「启动游戏」→ APK 向直播端拉 /api/config/dump → 落进私有覆盖层 game-overlay/
        ▼
GameServer 托管静态资源时**优先读覆盖层**（清单内路径不回落 assets）
        ▼
页面加载 constants.js → deepMerge(userConfig) → 覆盖 AIM.BY_DEVICE
        ▼
deviceProfile.getAimDeg() 运行时判定设备槽（pico / quest / steamvr / unknown）→ 取对应槽
        ▼
射线（input._applyRayAim）与子弹（input._rightAim）共用同一个角
```

关键点：**槽是按设备运行时选的**，所以同一份 `userConfig.js` 下发到 PICO 与 Quest，
两台机器**自动各取各的槽** —— 这正是现场要的效果，不需要在头显里输入任何东西。

### 4.2 PC 侧操作（`tools/set-aim.js`）

```bash
node tools/set-aim.js                       # 查看四个槽当前的角度（只读）
node tools/set-aim.js quest 14 -14 0        # 写 quest 槽
node tools/set-aim.js quest 12              # 只改 x（没写的轴原样不动）
node tools/set-aim.js pico -27 0 0 --dry    # 只打印将改成什么，不落盘
node tools/set-aim.js --file <path> ...     # 改别的 userConfig.js（如 EXE 指向的那份）
```

工具只做一件事：在 `userConfig.js` 里**原位替换** `<槽>: { x: .., y: .., z: .. }` 的三个数字，
保留原有缩进与行尾注释（`deepMerge` 是**递归合并**，所以只写一个槽不会把其它槽挤掉）。
它同时会打印「下一步」：重新点平台「启动游戏」让头显重拉配置即可。

### 4.3 现场两条路

| 路 | 用哪份 userConfig.js | 改完要做什么 |
|---|---|---|
| **直播端（EXE）下发**（现场主路） | EXE 指向的**游戏目录**里的 `src/core/userConfig.js` | 用 `--file` 指到那份，或直接编辑；下次 APK 启动自动重拉（换局号 ⇒ 旧覆盖层整目录作废再落新的） |
| **服务器清单**（`tools/cast-server/`） | 仓库里的 `src/core/userConfig.js` → 发布到 `content/<ver>/` | `node tools/cast-server/sync-content.js --ver 1.0.0`，再按 `docs/tech/09` 上传 |

> ⚠ 两条路的**清单必须逐字一致**（`sync-content.js` 的 `MANIFEST_ITEMS` 与 `cast-pc/main.js` 的 `CONFIG_MANIFEST`），
> 否则会出现「列表里有、包里没有」。本修没有改动这两处清单。

临时试角仍可用第四十三修的 URL 覆盖（只影响带参数的那台设备）：
`http://localhost:8080/?cast=1&pc=192.168.31.228&aim=14,-14,0`。
量好了再写进槽（上面这条命令）。

## 6. 踩坑（本修踩到的）

| 坑 | 说明 |
|---|---|
| **闩锁判据不能用「方向点积」** | 相邻帧点积只能识别「急转弯」，识别不出「已经绕到背后」。相机不在飞行线上时（本项目的常态：掌图沿 y=0、相机 y≈1.6），方向永远不会掉头 ⇒ 判据失效。正确判据是「沿飞行轴的投影符号」 |
| **单测的几何要和现场一致** | 旧单测把相机放在原点，于是旧判据「看起来是对的」。本修的新测试特意把相机放在 `(0, 1.6, 0)`，并**用反证①**（不给 `travelDir`）把「旧判据会转到 ~180°」也钉进测试里 |
| **`InstancedMesh` 的老坑继续有效** | 枪身环未点亮的点写**零缩放矩阵**；但这次干脆默认不画（`BARREL_DOTS=false`），因为现场反馈它在视野里挡东西 |
| **`renderer.compile` 的遍历口径** | r168：材质走 `scene.traverse`（**不看 visible**），灯光走 `traverseVisible` ⇒ 预热不必把穹顶显示出来；但**第三参 `targetScene` 必须是真场景**（`renderStates.get(targetScene)`） |
| **别对整个场景调 compile** | 那会把所有材质过一遍，影片期间就是一次明显卡顿。只把「待编译集合」限定成探针小场景（1 个 mesh） |
| **贴边方块会压到正文** | 底部积分/计数的基线原本在 `h-26`，方块贴底边会与它重叠 ⇒ 本次把基线抬到 `h-42`（并让右下的计数与左下的积分同一条基线） |
| **`deepMerge` 是递归合并** | 所以 `userConfig.js` 只写 `AIM.BY_DEVICE.quest` 不会把 `pico/steamvr/unknown` 挤掉；`set-aim.js` 也只需原位改数字 |

## 7. 验证方法

```bash
npm test                                          # 期望 112/112
node --import ./tests/register.mjs --test tests/stage3.test.mjs   # 单看本修这 4 例
node tools/set-aim.js                             # 四个槽的角度打印（只读，不改文件）
```

现场（按本修四条逐条看）：

1. **神掌**：攒够积分 → 扣左手 Grip 放如来神掌 → **盯着掌图穿过自己之后**的那一段：
   应该是「一张掌从面前掠过、背面朝你继续滑走」，**不再有 180° 翻转**。
2. **连杀计数**：连续用**子弹**击杀（技能杀的不算）→ 技能框边框上的方块一个一个亮；
   第 10 个触发加速 ⇒ 整圈闪一下 + 变金 + 右下角「杀敌 N/10」+ 枪身周围向后飘雾；
   加速期最多再攒 5 个（`BOOST_CARRY_MAX`），加速结束继续攒。
3. **开场黑边**：进入 VR → 开场影片播完 → **立刻左右转头**：不应再有黑边 / 明显顿挫。
   （看门狗兜底路径同理：`FALLBACK_DURATION_S` 到点也会走同一条交接。）
4. **按设备取参数**：`node tools/set-aim.js quest <新值>` → 改的是 `userConfig.js` →
   在 PC 上重新点平台「启动游戏」→ Quest 头显**不输入任何东西**，进游戏后射线应按 quest 槽生效；
   PICO 槽不受影响（两台机器各自读自己的槽）。

## 8. 边界与未决

- 本修**未实机验证**「开场黑边是否完全消失」：预热把已知的三项重活（下载/解码/上传、材质编译）挪走了，
  但若第 1 关还有别的首帧重活（例如某个模型首次上场），仍可能残留一次卡顿 —— 现场若仍看到，按 `docs/tech/13` 的
  `warmModelGpu()` 思路继续前移。
- 预热只在 `INTRO_VIDEO.ENABLED` 且「当前关有全景配置」时触发；不开场影片（非首关 / 非 VR）路径不走这里。
- `BARREL_DOTS` 打开时，枪身环与技能框**会同时显示**（画面重复但功能正常，未做互斥）。
- `SKILL_HINT.STREAK.DOTS` 与 `RAPID_FIRE.KILLS` 是**两个**配置：测试会断言两者一致，
  改其中一个务必同步改另一个，否则「方块亮满」与「触发加速」会错位。
- 瞄准角仍是**按厂牌共用一槽**（Quest 2/3/Pro 同槽）；换机型若仍偏，先用 `?aim=` 现场量，再写进槽。
- 本修**没有**新增网络协议、没有动平台上报（CMD 5/7/16）、没有动推流与门禁链路。
