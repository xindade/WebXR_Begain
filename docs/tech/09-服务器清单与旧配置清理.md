# 09 · 服务器清单与旧配置清理（第二十四修）

> **状态**：服务器侧 + PC EXE 侧 + 头显 APK 侧**均已实现并本机实跑通过**（见 §7）。
> **需求背景**（需求方 2026-09-24 拍板）：不再做加密狗式的服务器授权校验，
> 改成「**每次启动从服务器拉一份配置清单**」，并在**关闭游戏**与**下次启动前**把旧时间的配置清掉。
> **一句话差别**：以前是「授权过了就随包给配置」，现在是「**配置的唯一来源是服务器**」——
> 拿不到清单就不给配置，本地留的旧文件一律不作数。
> **关联**：`docs/tech/08-授权服务器与License方案.md`（被本方案降级为 `--license` 可选）、
> `docs/内容授权门禁设计.md`（同一思路的早期设计，差异见 §1）、
> `tools/cast-server/README.md` §10（服务器侧接口与发布流程）。

---

## 0. 一句话结论

**把关卡/数值配置从「随安装包分发」改成「每次启动向服务器拉清单」，并且「启动前 + 关闭游戏」各清一遍旧配置。**

它解决的问题不是「防盗版」，而是现场最常见的三类事故：

| 现场事故 | 本方案怎么兜住 |
|---|---|
| 换了台电脑 / 换了安装包，跑的却还是上一场的关卡数值 | 启动**无条件先清** + 重拉，配置只可能来自服务器 |
| 两次启动之间服务器改了数值，头显还在用缓存 | 清单按内容指纹换「局号」→ 头显整包重下 |
| 上一局结束、机器被平台 `kill`，旧配置留到下一局 | 「启动先清」是主防线（`before-quit` 在 kill 时根本不会执行） |

## 1. 与既有两套方案的关系（**别搞混，这是最容易出错的地方**）

| 项 | 08 · License（加密狗那套） | 内容授权门禁设计（Content Grant） | **09 · 服务器清单（本方案）** |
|---|---|---|---|
| 目的 | 防白嫖：没授权不给玩 | 防抄袭：内容本地不留源 | 配置集中管理 + 版本一致 + 不留旧配置 |
| 鉴权 | ECDSA 签名 license + Ke 绑机（PoP） | 服务器签名 + 绑机 | **共享密钥**（`manifestKey`），不绑机、不要激活码 |
| 强度 | 高（可离线验签，私钥不出服务器） | 高 | **低 —— 不是防破解**（密钥在客户端里） |
| 现状 | **已降级**：`LICENSE_ENABLED = hasFlag('license')`，正式包默认**关闭** | 设计定稿，**未实现** | **已实现，正式包默认开启** |
| 落点 | `tools/cast-pc/main.js` 的 License 段 | 未落地 | `tools/cast-server/server.js` §10 + `tools/cast-pc/main.js` 清单段 + `MainActivity.java` |

**诚实说明**：本方案**不能**防住有心破解的人 —— 清单密钥就写在 EXE 里（`MANIFEST_KEY` 默认 `webxr-manifest`）。
它挡的是「现场把旧配置留在机器上导致跑错版本」这类**运营事故**。真要防破解，回到 §1 第二列那套（Ks 签名 + 绑机）。

        │  GET /api/manifest?key=&ver=  → 200 { ok, files[] }  │
        └───────────────┬──────────────────────────────────┘

        └───────────────┬──────────────────────────────┘
                        │ ③ 头显取配置（既有 overlay 通道，未改协议）
                        ▼
        ┌──────────── 头显 APK ────────────┐

**三层清理点**（一一对应需求里的「关闭游戏」与「下次启动前」）：

| 时机 | 位置 | 说明 |
|---|---|---|
| ① **启动无条件先清** | `main.js` `onListen` → `manifestClear('启动前…')` | **主防线**。平台关局是 `kill`（实测与 `closeGame` 并发），`before-quit` 不会执行 |
| ② **本局结束** | `main.js` `roundSet(false)` → `manifestClear` + `manifestEnsure` | 清完立刻重拉，下一局开局即用新配置 |
| ③ 正常退出 | `main.js` `app.on('before-quit')` | 辅助 |
| ④ 头显启动 / 本局结束 | `MainActivity.clearOverlayCache()` | 见 §5 |

## 3. 服务器侧（`tools/cast-server/`）

### 3.1 发布一份清单：`sync-content.js`

```bash
# 用法（在项目根执行）
node tools/cast-server/sync-content.js --ver 1.0.0
# 也接受 --ver=1.0.0 写法

# 输出
tools/cast-server/content/manifest.json     { versions, current, updatedAt }
tools/cast-server/content/1.0.0/ver.json    { ver, builtAt, count, bytes, listSha256 }
tools/cast-server/content/1.0.0/src/content/{cards,eliteMonsters,enemies,levelConfig,levels,spawnPlans}.js
tools/cast-server/content/1.0.0/src/core/userConfig.js
```

- **发布范围**（`MANIFEST_ITEMS`，在 `sync-content.js` 内）必须与 EXE 的 `CONFIG_MANIFEST` **逐字一致**：
  `src/content/`（整目录）+ `src/core/userConfig.js`。改一处就要改两处。
- 整目录**重建**（先删后写），不是增量覆盖 —— 否则删掉一个关卡文件时服务器还留着它。
- `content/` 已加进 `tools/cast-server/.gitignore`：那是**发布产物**，不入库；服务器部署后**必须手动跑一次** `sync-content.js`。
- `ver.json` 的 `listSha256` = 全部文件 `path|sha256|size` 串起来的哈希，用于自证「这份清单没被动过」。

### 3.2 接口 `GET /api/manifest`

| 参数 | 必填 | 说明 |
|---|---|---|
| `key` | ✔ | 共享密钥，默认 `webxr-manifest`（服务器 `cfg.manifestKey`，可用环境变量 `MANIFEST_KEY` 覆盖） |
| `ver` | ✖ | 内容版本号；**缺省 = `current`** |

**响应 200**：

```json
{
  "ok": true, "ver": "1.0.0", "builtAt": 1790179414750, "count": 7, "bytes": 68939,
  "server": 1790180031041,
  "files": [ { "path": "src/content/levels.js", "sha256": "…", "size": 1357, "content": "…" } ]
}
```

**错误码（照抄进排障手册）**：

| HTTP | `why` | 含义 | 现场处置 |
|---|---|---|---|
| 403 | `badKey` | 密钥不对 | 两端 `manifestKey` / `--manifest-key` 不一致 |
| 404 | `noContentVersion` | 该 `ver` 没发布（响应带 `versions`） | 跑一次 `sync-content.js`，或把 EXE 的 `--content-ver` 改成已发布的版本 |

**⚠ 关键设计：`ver` 指定了就必须命中，绝不回落 `current`。** 一回落，现场「我明明发了 1.0.1，机器却在跑 1.0.0」就查不出来了 ——
宁可明确 404，也不要一个看起来正常的错版本。

其他：`manifestRatePerMin: 120`（每分钟限速）、`maxManifestBytes: 2MB`（响应体上限）、
`/api/health` 新增 `content: { dir, current, versions, updatedAt }`（服务器侧第一眼）。

`/api/manifest` 是**明文 HTTP 白名单接口**，与 license 那套签名协议完全独立（不做 Ke、不做 proof）。

## 4. PC EXE 侧（`tools/cast-pc/main.js`）

### 4.1 常量

| 常量 | 默认值 | 说明 |
|---|---|---|
| `MANIFEST_BASE` | `--manifest-url` → `LICENSE_BASE`（`https://webvr123.site`） | 清单站点基址 |
| `MANIFEST_KEY` | `--manifest-key` → `'webxr-manifest'` | ⚠ 与服务器 `cfg.manifestKey` 逐字一致 |
| `MANIFEST_VER` | `--content-ver` → `'1.0.0'` | ⚠ 必须等于服务器 `content/<ver>/` 目录名 |
| `MANIFEST_DIR` | `userData/manifest` | **不进 `GAME_ROOT`**（不污染游戏目录） |
| `MANIFEST_TMP` | `MANIFEST_DIR + '.tmp'` | 拉取中转目录（见 §8 原子替换） |
| `MANIFEST_TIMEOUT_MS` | `8000` | 单次请求超时 |
| `MANIFEST_RETRY_MS` | `[0, 2000, 5000, 10000]` | 启动时的 4 次重试节奏（现场刚开机 / 网络慢） |
| `MANIFEST_MAX_BYTES` | `4MB` | 响应体上限（防呆） |
| `MANIFEST_ON` | 打包版 **true** / 开发版 false | `--manifest` 强开、`--local-content` 强关 |

### 4.2 函数一览（都在 `main.js` 的「服务器清单 · 运行态」段）

| 函数 | 职责 |
|---|---|
| `manifestClear(reason)` | 删 `MANIFEST_DIR` + `MANIFEST_TMP`；重置运行态；记 `clearedAt/clearedWhy`；`pushStatus()` |
| `manifestPathOk(rel)` | **落盘闸**：拒绝 `../`、绝对路径、`C:` 前缀；只放 `CONFIG_MANIFEST` 允许的范围 |
| `manifestHttpGet(url)` | 带超时的 JSON GET（http/https 都认） |
| `manifestFetch()` | 拉 + 逐文件 sha256 自校验 + 落 tmp + **原子替换**；内容指纹变化时 `rotateSession()` |
| `manifestEnsure(reason)` | 唯一入口：按 `MANIFEST_RETRY_MS` 重试；**并发去重**；失败不回落 |
| `manifestManages(rel)` / `configBaseOf(rel)` | 按前缀分流：清单管辖的走缓存，其余仍走 `CONFIG_ROOT` |
| `manifestSummary()` | `/api/info` 与界面用的状态摘要 |
| `handleManifestStatic()` | `/src/content/**`、`/src/core/userConfig.js` 的静态服务（清单没就绪 → 404） |

### 4.3 启动时序（`onListen`）

```
① 打印「配置来源：服务器清单 <base>（期望 ver=…，落 …）」
② loadGuard()
③ if (MANIFEST_ON) {
     manifestClear('启动前…')          ← 先清（主防线）
     manifestEnsure('启动')             ← 再拉（4 次重试）
     ＋ 若 GAME_ROOT 里还留着 src/content/ ⇒ 警告「本地这份不会被使用」
   } else { 打印「清单模式关闭（--local-content / 开发模式）」 }
```

### 4.4 路由与失败语义

- `/api/info` → 新增 `manifest: { on, ok, why, ver, wantVer, base, dir, builtAt, fetchedAt, count, bytes, fp, tries, lastErr, clearedAt, clearedWhy }`
- 失败信息**自带现场指引**（本轮补）：HTTP 404 → 「服务器上没有 /api/manifest —— 多半是还没部署新版
  `server.js` + `content/`」；403 → 「清单密钥两端不一致」。实测见 §11.1。
- `/src/content/**` 与 `/src/core/userConfig.js` → **先于 `handleStatic`** 分流；清单未就绪返回 404 文本：

  ```
  404 —— 服务器清单未就绪，配置不下发（本地旧文件一律不作为回落）。
    why: 拉取失败：connect ECONNREFUSED …
    排障：本 EXE 的 /api/info → manifest 字段；服务器 GET /api/health → content 字段。
  ```

- `POST /api/config/dump`（`handleConfigDump` 已改 `async`）：凭据校验后 `await manifestEnsure('配置下发')`，
  失败回 `{ allow:false, why:'配置下发失败：…（配置只认服务器清单，已停用本地回落；应急可加 --local-content 用本地游戏目录）' }`。
- `roundSet(false)` → 清 + 重拉（§2 表 ②）。
- 接收端界面新增 `#mftbox`：一行显示「清单 就绪/未就绪 · ver · 文件数 · 指纹 · 上次清理时间与原因」。

### 4.5 `--local-content` 的分流口径

`--local-content`（或开发模式）下：`manifestManages()` 仍判 true，但 `handleManifestStatic()` 直接
**交回 `handleStatic()`**，即「配置仍从游戏目录出」—— 这是**应急/自测口子**，正式包不要加。

## 5. 头显 APK 侧（`MainActivity.java`）

新增 `static void clearOverlayCache(String why)`：删 `filesDir/game-overlay` 整目录 +
`SharedPreferences("cast").remove("overlaySession")` + `sServer.setOverlay(null, null)` + `sOverlayCount = 0`。

| 调用点 | 条件 | 为什么 |
|---|---|---|
| `onCreate`（`mountOverlayToServer()` **之前**） | `if (!passThrough)` | 「下次启动前清理旧配置」。⚠ **`passThrough` 例外是必须的** —— 平台重拉且游戏页仍活着时，那一刻删文件会把玩家当场踢出 VR |
| `scheduleClientRestore` 回调（`restoreClientAndCloseBrowser()` 之前） | `if (!sPcConfigured \|\| GameServer.sCastRoundOver)` | 「关闭游戏」清理；否则只打留痕跳过 |

**⚠ 没清成功的表现**：头显第二次进游戏时仍在跑上一局的关卡数值 —— 与 PC 侧「清单没拉到」是两种不同现象，排障时先看哪一端。

## 7. 验证方法（**本轮实测记录，可照抄复现**）

### 7.1 前置：起一个本地服务器 + 发布一份内容

```powershell
node tools/cast-server/sync-content.js --ver 1.0.0
$env:PORT='8796'; $env:HOST='127.0.0.1'; $env:DATA_DIR="$env:TEMP\srv-test"
node tools/cast-server/server.js
# 另一窗口
curl "http://127.0.0.1:8796/api/health"     # → content: { current:"1.0.0", versions:["1.0.0"] }
```

### 7.2 正例：清单就绪

```powershell
# 正式包（dist/win-unpacked/WebXR直播接收端.exe）或开发模式加 --manifest
WebXR直播接收端.exe --port=18470 --manifest-url=http://127.0.0.1:8796
curl "http://127.0.0.1:18470/api/info"      # manifest.ok=true count=7 bytes=68939 fp=…
curl "http://127.0.0.1:18470/src/content/levels.js"   # 200（内容来自清单缓存）
```

**本轮实测结果**：`ok=true, ver=1.0.0, count=7, bytes=68939, fp=ae06e1354398aeb2, tries=1`；
`/src/content/levels.js` → 200（长度 1247）；`/src/core/userConfig.js` → 200（25160）；
`/api/config/dump` → `allow=true count=7`，7 个文件与项目源**逐字一致**；
`userData/manifest/src/content/` 下 6 个文件 + `meta.json`（ver/builtAt/fetchedAt/count/bytes/fp）；
打包版日志含「配置来源：**服务器清单**」。

### 7.3 反例：服务器不可达（**必须明确失败，且不回落**）

```powershell
# 先往 userData 里放一份「上一局残留」的旧配置，再启动一个指向死地址的 EXE
WebXR直播接收端.exe --port=18462 --manifest-url=http://127.0.0.1:8799 --user-data-dir=<临时目录>
```

**本轮实测结果**：

- 启动 3 秒后：残留旧配置**已被清空**（`manifestClear` 先于拉取执行）；
- `/src/content/levels.js` → **404**（不回落）；
- 25 秒后 `/api/info.manifest` → `{ ok:false, why:"拉取失败：connect ECONNREFUSED 127.0.0.1:8799", tries:4 }`；
- 日志逐条：`清单拉取第 1/4 次失败…` … `第 4/4 次失败…` → `✖ 服务器清单不可用（启动）`。

### 7.4 本局结束清理 + 重拉

```powershell
curl -X POST http://127.0.0.1:18463/api/round/start -d '{"why":"测试"}'
curl -X POST http://127.0.0.1:18463/api/round/end   -d '{"why":"测试本局结束"}'
```

**本轮实测结果**：结束后瞬间缓存已清、4 秒内已重拉；`/api/info.manifest.clearedWhy = "本局结束（画面侧上报：测试本局结束）"`；
重拉后 `ok=true`、静态取配置 200。

### 7.5 自动化回归脚本

本机夹具：`%TEMP%\p24rt3.cjs`（正/反例一次跑完）、`%TEMP%\p24rt4.cjs`（清旧配置 + 本局结束重拉）、
`%TEMP%\p24pkg.cjs`（**打包版**实跑）。改任何清单相关代码后至少跑前两个。

## 8. 踩坑（都是本轮真实踩到的）

| # | 坑 | 现象 | 结论 |
|---|---|---|---|
| 1 | **函数插错作用域** | 启动日志有「配置来源：服务器清单」，但后面完全没有网络请求；`/api/info` 里 `manifest` 恒为初始值 | 补丁把 `manifestClear` 等函数**插进了 `onListen` 内部的注释段**（模块级函数声明会被提升，写在任何位置都能用；**写在别人函数体内不能**）。异常被临时 try 吃掉 ⇒ 表现为「静默不执行」。**改多函数的大补丁后必须 `node --check` + 实跑看日志** |
| 2 | 拉取当场写缓存 | 断网时留下「一半新一半旧」的配置 | 一律**先落 `MANIFEST_DIR + '.tmp'` 再 `rename` 原子替换** |
| 3 | 清单没就绪就回落本地 | 现场「配置没拉到但游戏照跑」，跑的是旧数值 | 口径与头显侧「只认下发、不回落 assets」统一：**404 / allow:false**，应急才 `--local-content` |
| 4 | `ver` 不存在时回落 `current` | 「我发了新版，机器却在跑旧版」查不出来 | 服务器**明确 404 `noContentVersion`**（响应带 `versions`） |
| 5 | 启动清理只靠 `before-quit` | 平台关局是 `kill`，事件不执行 → 旧配置留到下一局 | **「启动无条件先清」才是主防线**，`before-quit` 只是辅助 |
| 6 | 头显 `passThrough` 时清覆盖层 | 平台重拉那一刻删文件 ⇒ 玩家当场被踢出 VR | 启动清理要加 `if (!passThrough)` 例外 |
| 7 | 换局号太随意 | 内容没变也换 ⇒ 所有头显白重下配置 | 只在**内容指纹变化**时 `rotateSession()` |
| 8 | `why` 停在中间态 | 重试期间 `/api/info` 只显示「已清理，待拉取」 | 每次失败**就地更新** `MANIFEST.why`/`lastErr`（现场排障第一眼就是它） |

## 10. 已知限制（诚实边界）

- **不是防破解**：`MANIFEST_KEY` 在客户端里，改包即绕过。它的价值是「配置集中管理 + 版本一致 + 不留旧配置」。
- **服务器成了软单点**：拿不到清单 = 头显起不来游戏。现场必须有应急路径：`--local-content` + 游戏目录自带的配置。
- **首次部署容易漏**：`content/` 是 `.gitignore` 的发布产物，`git pull` 之后**必须**跑一次 `sync-content.js`。
- **目前只有 `1.0.0` 一个版本**：多版本并存（灰度/回滚）已支持（`ver` 参数 + `manifest.json.versions`），但尚未实操过。

### 11.2 兼容性说明（部署不会打断现场）

- `/api/manifest` 是**纯新增**接口；`license` 那一组接口与 `ProtectSystem=strict` 口径均未改动。
- `/api/health` 只是**多了一个 `content` 字段**，老客户端读它不会出错。
- `content/` 目录对服务是**只读**的（`ProtectSystem=strict`），而 `/api/manifest` 只需要读 —— 实测全部是
  `readFileSync` / `readdirSync`，无需放宽 systemd 权限。
- 版本回滚：把旧的 `server.js` 传回去重启即可；`content/` 留着不影响旧接口。
